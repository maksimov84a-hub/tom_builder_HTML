# Программа «Сборка тома проектной документации по ГОСТ Р 21.101-2020»

Проектная спецификация (разработка).

> Статус: **реализовано (прототип)**. Главный интерфейс — **HTML-предпросмотр листов** (QWebEngineView внутри Qt), поля редактируются inline, общие реквизиты и подписи обновляются во всех листах.

---

## 0. Сводка решений

| Вопрос | Решение |
|--------|---------|
| Стек | **Python** |
| GUI | PySide6 (Qt) |
| DOC-экспорт | обложка + титульный лист + содержание + пояснительная записка (без графики) |
| PDF-экспорт | **полный том**: текст (А4) + графика (родные размеры листов) + приложения |
| Doc→PDF | **Word COM** (Word установлен у пользователя) |
| Шрифт | **ISOCPEUR** везде; кегль зависит от расположения |
| Обложка | **Приложение Е ГОСТ** — первый лист; авто по ГОСТ или кастомный шаблон |
| Титульный лист | **Приложение Ж ГОСТ** — второй лист; авто по ГОСТ или кастомный шаблон |
| ПЗ из DOCX | **Переоформление** под ГОСТ (не «как есть») |
| Подписи | изображения, встраиваются в графы по совпадению **Фамилии** |
| Изменения | **Журнал/лист регистрации изменений** (форма из ГОСТ), в конце тома |
| Приложения | **PDF-файлы**, вставляются в том **без рамки** (самостоятельный документ), с нумерацией и в содержании |
| Поля листа | стандарт ГОСТ: левое 20 мм, остальные 5 мм |

## 1. Назначение

Десктопная программа для **Windows**, которая принимает набор готовых документов проектировщика (Word + PDF, разные форматы листов) и собирает из них **единый том**, оформленный по **ГОСТ Р 21.101-2020**, с выдачей в **DOC** и **PDF**.

Пользователь — один **проектировщик** на своём ПК. Требований к защите и многопользовательскому режиму нет.

---

## 2. Состав тома

Том = **пояснительная записка** (текст, листы А4) + **графическая часть** (чертежи произвольных форматов) + **приложения** + **журнал изменений**.

```
ТОМ
├── Обложка                  (приложение Е ГОСТ — первый лист)
│     ├── авто по ГОСТ  ИЛИ  кастомный шаблон организации
├── Титульный лист            (приложение Ж ГОСТ — второй лист)
│     ├── авто по ГОСТ  ИЛИ  кастомный шаблон организации
├── Содержание / Опись        (перечень разделов, листов, приложений) — лист 1
├── Состав проектной документации (таблица томов, формы 5/6) — лист 2
├── Пояснительная записка     (текст, листы А4)
│     ├── оглавление           — АВТО по уровням заголовков DOCX (см. §5.6)
│     ├── первый лист          — основная надпись форма 2
│     └── последующие листы    — основная надпись форма 2а
├── Графическая часть          (листы произвольных форматов)
│     └── каждый лист          — рамка + основная надпись форма 1
├── Приложения                 (PDF-файлы, нумеруемые, с заголовком «Приложение …»)
└── Лист регистрации изменений (журнал внесения изменений)
```

> Порядок следования блоков в томе — **настраиваемый** (шаблон структуры). По умолчанию приложения идут после графической части, лист регистрации изменений — в конце тома.

## 3. Модель данных тома

Проект тома = сохраняемый файл (JSON/XML), чтобы том можно было **пересобрать** при изменении исходников.

### 3.1 Реквизиты тома (форма ввода)

- наименование организации (проектной организации);
- обозначение/шифр тома;
- наименование объекта;
- наименование тома (раздела);
- стадия: **«Проектная документация»** / **«Рабочая документация»** — выбирается из двух значений;
  на обложке и титульном листе выводится полное наименование, в графе «Стадия» основной надписи
  — обозначение **«П»** / **«Р»** (`models.STAGE_LABELS`, `stage_label()`, `parse_stage()`);
- город, год;
- список разделов и их листов (для содержания);
- параметры листа (поля по ГОСТ, масштаб/ориентация графических листов).

### 3.2 Реестр подписантов (для подписей)

```
Фамилия | Имя/Отчество | Должность | Роль              | Изображение подписи
--------|--------------|-----------|-------------------|--------------------
Иванов  | И.И.         | ГИП       | Утв./Разраб.       | sig_ivanov.png
Сидоров | С.С.         | Нач. отд. | Пров./Н.контр.     | sig_sidorov.png
```

**Ключевая логика:** в каждой графе основной надписи и на титульном листе указывается **Фамилия**; программа ищет совпадение в реестре и подставляет соответствующее изображение подписи. Если подписи нет — выводится предупреждение.

### 3.3 Журнал (реестр) изменений

Таблица вносимых изменений — основа для генерации «Листа регистрации изменений».

```
№ изм. | Дата    | Содержание изменения        | Раздел/Лист | Исполнитель | Подпись  | Статус
-------|---------|------------------------------|-------------|-------------|----------|---------
1      | 12.03.2 | Замена таблицы в ПЗ, л. 5   | ПЗ, л. 5    | Иванов      | (изобр.)  | Внесено
2      | 18.03.2 | Корректировка генплана      | Графика, л.2| Сидоров     | (изобр.)  | Внесено
```

Поля записи изменения:
- **№ изменения** (порядковый);
- **дата**;
- **содержание изменения** (что изменено);
- **раздел/лист** (привязка к месту в томе);
- **исполнитель** (Фамилия → автоматическая подпись из реестра);
- **статус** (внесено / в работе / отменено).

### 3.4 Приложения

```
№ | Наименование приложения     | Файл (PDF) | Раздел-привязка | Листы (авто)
--|-----------------------------|------------|------------------|-------------
А | Спецификация оборудования   | app_A.pdf  | ПЗ               | 1–3
Б | Техническое задание         | app_B.pdf  | —                | 1–2
```

Поля приложения:
- **номер** (буквенный «А, Б, В…» или числовой — настраивается);
- **наименование**;
- **файл PDF**;
- **раздел-привязка** (опционально);
- **листы** (вычисляются автоматически из PDF).

### 3.5 Источники (вход)

- текстовые **DOCX** → в пояснительную записку;
- графические **PDF** → в графическую часть;
- **PDF** → в приложения;
- порядок и состав разделов настраиваются в дереве тома (UI).

## 4. Функциональные требования

### 4.1 Сборочное задание
- создание/редактирование проекта тома;
- задание структуры: титул → содержание → ПЗ → графика → приложения → лист изменений;
- добавление документов в разделы, настройка их **порядка**;
- сохранение/загрузка проекта тома.

### 4.2 Ввод реквизитов
- единая форма реквизитов (см. §3.1);
- сохранение и подстановка во все шаблоны (титул, содержание, каждая основная надпись).

### 4.3 Оформление по ГОСТ (конфигурируемый слой)
- рамка: левое поле 20 мм, остальные 5 мм;
- основная надпись по формам **3 / 5 / 6** на соответствующих листах;
- титульный лист и содержание по шаблонам;
- шрифт **ISOCPEUR**, кегль по карте «расположение → кегль» (§5);
- сквозная нумерация листов и перекрёстные ссылки («Лист N», «Листов M»).

**Единая толщина и совпадение линий.** Рамка листа, сетка основной надписи и
квадрат сквозной нумерации рисуются **одним приёмом** — полосой с осью ровно на
координате (`preview_html._rule_h` / `_rule_v`, толщина `LINE_MM = 0.25` мм):

| Где | Как рисуется | Толщина |
|-----|--------------|---------|
| HTML-предпросмотр / собранный HTML | полосы `_frame_rules()` / сетка штампа / `_sheet_number_rules()` | 0.25 мм |
| PDF (PyMuPDF) | `draw_rect(..., width=LINE_WIDTH_PT)` | 0.25 мм (`LINE_WIDTH_PT = 0.7`) |
| Word (DOCX) | `w:pgBorders` для рамки + границы ячеек штампа | 0.75 pt (`docx_tables.LINE_BORDER_SZ`) |

Раньше рамка рисовалась CSS-`border` (штрих уходит **внутрь** блока), а линии
штампа — отдельными `div` с `border-left/top` (штрих уходит **наружу** от
координаты). На стыке получались две параллельные линии в 0.25 мм друг от
друга — рамка и штамп «не совпадали». Квадрат нумерации страдал тем же. Теперь
все линии центрируются на своей координате, поэтому крайние линии штампа и
стороны квадрата ложатся ровно на рамку (проверено замером: разброс 0.000 мм).

Дополнительно: в PDF лист создаётся размером **ровно A4** (`gost.A4_W_PT` /
`A4_H_PT` = 595.276 × 841.890 pt). Округление до «595 × 842» давало ширину
209.9 мм — правая линия рамки вставала на 204.9 и расходилась с правой линией
штампа (205.0).

**Квадрат нумерации.** Все четыре его стороны рисуются всегда, даже когда
верхняя и правая совпадают с линиями рамки. У квадрата есть белая подложка под
цифру (`z-index:3` выше рамки), она перекрывает половину толщины линии рамки, и
верхняя граница выглядела непрорисованной. Линии квадрата лежат в слое выше
подложки (`z-index:4`), ложатся точно на линию рамки и второй линии не
образуют.

Координаты квадрата считаются от **фактической ширины листа**
(`_sheet_number_rules(page_w_mm, page_h_mm)`), а не от A4: у графической части и
приложений формат свой (A1, A2, A3…), и привязка к A4 уводила квадрат в середину
листа, оставляя цифру в углу без рамки. Цифра позиционируется CSS
(`right:5mm; top:5mm` от листа), поэтому при своём формате линии и цифра
совпадают.

**Правила и шаблоны выносятся в конфигурацию/шаблоны**, а не зашиваются в код.

### 4.6 Графическая часть в предпросмотре и скорость переключения

**В предпросмотре листы графической части НЕ рендерятся.** Показывается пустой
лист своего формата с квадратом сквозной нумерации и надписью «Лист
графической части N» по центру — этого достаточно, чтобы листать раздел и
сверять номера с содержанием. Растр чертежей в предпросмотре не нужен: он
тяжёлый и не участвует в сборке (в PDF графика попадает вектором из исходного
файла). Режим включается флагом `snapshot["preview_blank_graphic"]` в
`_all_section_fragments`; приложения и ПЗ-PDF рендерятся как раньше.

**В собранном HTML-томе листы графики остаются** — со страницами и нумерацией
(`build_volume_html` / `build_section_html` флаг не ставят). Поэтому нумерация
в предпросмотре и в собранном томе совпадает.

Переключение раздела не должно занимать секунды. Дорогие операции кэшируются:

| Что | Как ускорено |
|-----|--------------|
| Разбор DOCX (`read_docx`) | кэш по (путь, время изменения, размер) — `docx_reader`; за одно переключение один и тот же файл читался до 10 раз |
| Разбивка DOCX на листы (`_paginate_docx`) | кэш по (файл, форма первого листа, кегли текста ПЗ) — считается один раз на файл вместо 4 раз |
| Картинки страниц PDF | кэш base64 по (файл, страница, разрешение); раньше ВСЕ страницы встраивались в HTML при каждой перерисовке |
| Размеры страниц PDF | кэш по (файл, номер страницы) |

Кэши сбрасываются сами: ключ включает время изменения и размер файла, поэтому
любая запись (автосохранение правки, пересборка) делает старые записи
недействительными. Дополнительно есть `docx_reader.clear_docx_cache(path)`.

**Замер (том из 169 страниц графики, 6 PDF):** переключение на «Графическую
часть» — 12500 → 34 мс, HTML 56 МБ → 197 КБ; ПЗ из 16 листов — 517 → 14 мс.

**Сохранение активного листа при перестройке дерева.** `SheetTree._refresh`
перестраивает дерево через `tree.clear()`; `QTreeWidget` при этом сам двигает
`currentItem` и шлёт `currentItemChanged` — в том числе с `cur=None` и с
«первым» элементом. Обработчик выбора такие события не принимает: он сразу
выходит, пока поднят флаг `_updating` (`_on_select`). Иначе любой путь с
`set_project` — завершение пересчёта страниц ПЗ, сохранение правок записки,
закрытие редактора ПЗ — «перебрасывал» предпросмотр на другой раздел: при
открытом документе ПЗ за один пересчёт приходило четыре ложных выбора
(Состав → Содержание → Титул → Обложка), и активным оставался лист «Обложка».
Восстановление прежнего выбора выполняет `_restore_selection`, блокируя сигналы.

### 4.6.1 Пересчёт страниц ПЗ средствами Word (скорость)

Пересчёт раскладки записки — самая дорогая операция в работе с ПЗ: Word реально
раскладывает документ, и результат нужен для сквозной нумерации, содержания и
штампов. Замер на записке 16 листов (238 абзацев, 4 таблицы, 253 закладки
`MIMO_*`): **22 с → 6.7 с** на документ.

| Что | Как ускорено |
|-----|--------------|
| Номер страницы позиции (`word_com`) | вместо COM-вызова `Range.Information(3)` на каждую закладку (506 обращений по ~30 мс = ~15 с) номер берётся сравнением позиции с заранее собранными началами страниц (`bisect`). Результат совпадает с прежним до последнего символа |
| Старт Word (`DispatchEx`) | один экземпляр `Word.Application` на весь пакет документов (`word_application` в `PaginationWorker` и `BuildWorker`), а не свой на каждый: запуск стоит ~2 с. На двух записках 13.4 → 6.1 с, на трёх 20.2 → 8.6 с |
| Подготовка копии (`_normalized_copy`) | читаются только форматы абзацев (`docx_reader.paragraph_formats`) вместо полного `read_docx`: 0.25 → 0.045 с |
| Разрешение стилей абзаца | `docx_reader.style_name_of` кэширует имя стиля по `styleId` на документ: `paragraph.style` поднимает `styles.xml` при каждом обращении (0.27 → 0.004 с на 238 абзацев) |

**Почему нельзя просто взять `styleId` вместо имени стиля.** У типовых записок
идентификаторы стилей числовые (`w:styleId="1"` / `"20"`), а человекочитаемые
имена (`heading 1`, `heading 2`) лежат отдельно в `styles.xml` — на проверочном
файле прямая замена потеряла бы 18 заголовков из 18. Поэтому кэшируется именно
**имя** стиля, разрешённое через python-docx.

**Ограничения и проверки.** Экземпляр Word создаётся в том же потоке воркера,
где живёт вызов: COM-объект нельзя переносить между потоками без маршалинга.
Правильность подтверждена сверкой полной карты страниц (`paragraphs`, `tables`,
`page_count`) с прежней реализацией — совпадение бит-в-бит на 253 закладках.
Кэш раскладки на диске (`layout.json` рядом с DOCX) сохранён без изменений,
поэтому повторный пересчёт без правки файла по-прежнему мгновенный.

### 4.4 Вставка подписей
- импорт изображений подписей (скан/рисунок) в реестр;
- автоматическое размещение подписи в графе по совпадению Фамилии;
- контроль: предупреждение при отсутствии подписи/исполнителя в графе.

### 4.5 Записи о внесении изменений
- **форма/таблица** внесения записей об изменениях (см. §3.3);
- ведение **журнала** изменений в рамках проекта тома;
- **автогенерация «Листа регистрации изменений»** по **форме из ГОСТ Р 21.101-2020** (жёстко по таблице, без ручной настройки) и вставка в том;
- автоматическая подстановка **подписи исполнителя** по Фамилии;
- пересчёт сквозной нумерации листов при внесении изменений;
- отражение изменений в содержании и (при необходимости) в ведомости «Состав проектной документации»;
- статус изменения (внесено / в работе / отменено) и учёт в отчёте о сборке.

### 4.6 Вставка приложений (PDF)
- добавление приложений **PDF** с назначением номера и наименования;
- автоматическое вычисление количества листов приложения;
- вставка приложений в том **в конец** (место настраивается), с заголовком «Приложение …»;
- автоматическое **внесение приложений в содержание**;
- оформление приложений в томе: **БЕЗ чертёжной рамки и осн. надписи** — как самостоятельный документ, только с заголовком «Приложение …» (подтверждено пользователем).

### 4.7 Предпросмотр и проверка
- постраничный предпросмотр (текст) и полистовой (графика, приложения), с рамками и основными надписями;
- отчёт о сборке: включённые листы/приложения, порядок, ошибки (нет файла, битый PDF, несоответствие формата, отсутствует подпись, незаполненное изменение);
- контроль сквозной нумерации и полноты реквизитов перед экспортом.

### 4.8 Экспорт
- **DOC**: сгенерированные листы (обложка, титул, содержание, состав ПД, перечень
  листов ГЧ, лист регистрации изменений) + **текст ПЗ из исходных DOCX** с
  оформлением по ГОСТ. **Страницы исходных PDF (графика, приложения) в DOCX не
  выводятся** — они не переносятся редактируемым текстом, а вставка картинками
  делает файл нередактируемым; вместо листов печатается только перечень листов
  ГЧ и титульные листы приложений («Приложение N», наименование, «Листов: N»);
- **DOC по разделам**: сборка того же состава **отдельным файлом на каждый раздел
  тома** (`docx_exporter.build_chapters_docx`, флажок «DOC — по разделам» в окне
  сборки, настройка `Config.build_docx_chapters`). Имя файла — обозначение
  раздела + подпись («02-2026-ТР.ПЗ Пояснительная записка.docx»);
- **PDF**: полный том (текст + графика + приложения + лист регистрации изменений).

**Основная надпись в DOCX: первый лист текстового раздела — форма 3, последующие —
форма 6** (`gost.FORM_TEXT_FIRST_WORD`, по сверке с образцами `форма3_сверка.docx` и
`форма_6 (2).docx` в корне проекта). У формы 3 (185 × 40) обозначение занимает всю
верхнюю полосу 65…185 мм, а в левом блоке над строкой заголовков печатаются два ряда
значений таблицы изменений; у формы 5 эта полоса (135…185 × 0…15 мм) оставалась
пустой, а строк значений в таблице изменений не было.
Расхождение намеренное и касается **только Word**: HTML-предпросмотр и PDF продолжают
выводить форму 5 (`FORM_TEXT_FIRST`), поэтому сетки штампа в предпросмотре и в DOCX
могут не совпадать. Бюджет пагинации от этого не меняется — у форм 3 и 5 одинаковая
высота 40 мм.

## 5. Карта шрифта «расположение → кегль» (ISOCPEUR)

Кегль не задан жёстко, а берётся из конфигурационной карты:

```
область применения                    | кегль (пример, настраивается)
--------------------------------------|------------------------------
титульный лист (наименование тома)    | крупный (напр. 18)
основная надпись (обозначение тома)   | средний (напр. 14)
основная надпись (графы, ФИО)         | по типу графы (напр. 10)
содержание / заголовки                | по иерархии
текст пояснительной записки           | кегль по регламенту (напр. 14)
заголовок приложения / лист изменений | средний (напр. 12)
должности / расшифровки подписей      | свой (напр. 10)
```

Карта хранится в конфигурации → кегли меняются без правки кода.

> **Техническое замечание по ISOCPEUR.** Это векторный/чертёжный шрифт ГОСТ, предназначенный в первую очередь для графики (рамки, осн. надписи, размеры). Он точно воспроизводится в **векторной** отрисовке PDF (PyMuPDF/reportlab). Для текста ПЗ в Word он отрисовывается корректно только если ISOCPEUR установлен в системе; иначе нужен fallback. **Решение принято: используем ISOCPEUR во всех элементах** (подтверждено пользователем).

## 5.5 Предпросмотр в HTML (главный интерфейс)

> **Статус: реализовано.** Предпросмотр листов выполняется в **HTML** и встраивается в окно Qt через `QWebEngineView` + `QWebChannel` (JS↔Python мост).

### Компоновка окна

```
┌────────────┬──────────────────────────────┬──────────────────┐
│  Листы     │   HTML-предпросмотр листа    │  Контекстные     │
│  тома      │   (рамка + поля + осн.       │  настройки       │
│  (слева)   │    надпись), fit-to-window   │  [Подписанты…]   │
│            │                              │  (стек форм)     │
├────────────┴──────────────────────────────┴──────────────────┤
│ Основная надпись листа  185 × 40 мм   масштаб 100%  [Свернуть]│
│                     ┌─────────────────────┐                   │
│                     │  нижний штамп листа │                   │
│                     └─────────────────────┘                   │
└───────────────────────────────────────────────────────────────┘
```

- **Слева** — дерево «Листы тома» = **редактор структуры**: разделы тома (обложка, титульный лист, содержание, ПЗ, графика, приложения, лист изменений) в настраиваемом порядке. **Показываются только разделы** — документы и приложения в дерево не выводятся (ими управляет контекстная панель справа, блок «Документы раздела»).
- **Центр** — HTML-предпросмотр выбранного пункта (масштабируется под окно). Показываются **все листы** пункта:
  - **документ ПЗ (DOCX)** — **все его листы подряд** той же пагинацией, что и при сборке
    (`render_sheet_fragments` → `_docx_sheet_fragments`); первый лист — форма 5, последующие — форма 6;
  - **документ графики / приложение (PDF)** — все страницы PDF;
  - **раздел «Пояснительная записка» / «Графическая часть» / «Приложения»** — все листы раздела
    целиком (графы «Лист/Листов» штампа — по разделу, квадрат сквозной нумерации — сквозной по тому);
  - **обложка / титул / содержание / изменения** — один лист.
  Число показанных листов выводится в панели предпросмотра («Листов: N»). Если файл недоступен
  или не читается — информационная заглушка.
- **Внизу окна** — панель **основной надписи активного листа** (`app/ui/stamp_panel.py`,
  `StampPanel`). Показывает нижний штамп листа, который занимает большую часть окна
  предпросмотра: при прокрутке к другому листу надпись меняется (`bridge.onActiveSheet` →
  `preview.active_stamp_changed` → `StampPanel.set_active`), активный лист сохраняется и при
  перерисовке набора. Масштаб — **100 %**: размеры штампа заданы в миллиметрах, а CSS-миллиметр
  равен физическому, поэтому панель показывает надпись в натуральную величину; её высота
  считается по высоте штампа (`extract_stamp_html` / `stamp_size_mm`) плюс поля 4 мм. Кнопка
  **«Свернуть»** превращает панель в узкую полосу внизу окна (26 px, «Развернуть» возвращает);
  состояние хранится в `config.json` (`Config.stamp_panel_open`). У обложки и титульного листа
  надписи нет, вместо неё выводится пояснение.
  **Поля панели редактируются так же, как на самом листе:** панель подключается к тому же
  `PreviewBridge` (свой `QWebChannel`), поэтому правка уходит в модель теми же ключами
  (`organization`, `volume_id`, `sp|<раздел>|<строка>|post`, `ss|…|surname`, `ch|…`), клик по
  полю подписи открывает выбор подписанта, а правка фамилии сразу подставляет подпись из
  реестра (`_signer_registry_html` передаётся в панель вместе с надписями). Работают подсказки
  пустых полей и автоподгонка кегля графы 9.
  **Сохранение — по потере фокуса** (`blur`/`focusout`), а не по каждой букве: во время ввода
  обновляется только вид поля (подсказка, подпись по фамилии), а в модель значение уходит при
  уходе из поля; Enter завершает ввод тем же путём (перенос строки в ячейке не создаётся).
  Повторный уход фокуса без правок ничего не отправляет (сравнение с значением на момент
  фокуса), при сворачивании панели недописанное значение дописывается (`_commit_pending`).
  После записи листы перерисовываются (`main_window._on_panel_field_changed` →
  `_refresh_preview`), поэтому **все связанные штампы** — на остальных листах пункта, в
  содержании и в самой панели — сразу показывают новое значение.

**Квадрат сквозной нумерации (правый верхний угол) в предпросмотре — сквозной по тому.**
Номер листа в квадрате считается от первого листа раздела по `toc.build_layout`
(`_section_square_base`), поэтому он совпадает с номером в содержании и с собранным HTML:
раздел ПЗ после содержания начинается не с 1, а со своего номера в томе. Графы
«Лист»/«Листов» самой основной надписи при этом остаются **по разделу** — это разные
графы с разным смыслом. Без базы (сборка отдельного раздела через `build_section_html`)
квадрат локальный, раздел нумеруется с 1.

### Лист «Графическая часть» с перечнем листов

> **Статус: реализовано.** Перед листами графической части вставляется лист с
> рамкой и основной надписью **формы 3**: заголовок «Графическая часть»,
> подзаголовок «Перечень листов графической части» и таблица **во всю ширину**
> листа с колонками **Обозначение | Наименование | Примечание**.

| Что | Как |
|-----|-----|
| Включение листа | `project.graphic_sheet_list.enabled` (по умолчанию включён) |
| Заголовок / подзаголовок | `graphic_sheet_list.title` / `subtitle` |
| Источник строк | `source = "pdf"` — из штампов PDF-листов (по умолчанию); `"auto"` — по листам раздела; `"excel"` — из книги `.xlsx` |
| Шаблон обозначения | `designation_template`, по умолчанию `{volume} л.{no}` |
| Области штампа | `name_box`, `number_box` (мм от края листа) |
| Файл Excel | `excel_path` (+ `sheet_name` — имя листа книги, пусто = первый) |
| Единый источник строк | `preview_html.build_graphic_sheet_list(project)` |

**Данные листа берутся из самого PDF (`source = "pdf"`).** Штамп на листе
стоит в правом нижнем углу с отступом 5 мм от правого края и от низа; все
размеры отсчитываются **от края листа**, поэтому геометрия не зависит от
формата (A4/A3/A1) и ориентации (`app/core/sheet_stamp.py`):

| Что | Область | По умолчанию |
|-----|---------|--------------|
| Название листа | влево 55..125 мм, вверх 5..20 мм | `models.SHEET_NAME_BOX` |
| Номер листа | влево 25..40 мм, вверх 20..30 мм | `models.SHEET_NO_BOX` |

**Главное правило: если название или номер в своих квадратах не найдены, лист
в перечень НЕ ПОПАДАЕТ.** Так отсеиваются титулы, схемы без штампа и служебные
страницы. Проверено на реальном файле: из 29 страниц распознаны ровно 4 — те,
где есть настоящий штамп, остальные 25 отброшены.

Обозначение листа собирается по шаблону: по умолчанию **шифр + «л.» + номер**
(«A1-003.24-КР.ГЧ л.16»). Шифр — обозначение раздела (`{volume}`), номер —
из штампа (`{no}`). Номер принимает цифры и буквенный индекс («12а»).

**Ширины колонок — 50 / 95 / 40 мм** (`models.SHEETLIST_WIDTHS`): Обозначение |
Наименование | Примечание. Единый источник для предпросмотра, Word и PDF.

**Таблица упирается в рамку листа.** Сумма ширин 50 + 95 + 40 = **185 мм** — это
ровно расстояние между линиями рамки A4 (210 − 20 − 5). Текстовая область
предпросмотра имеет внутренний отступ 6 мм с каждой стороны, поэтому блок с
таблицей выводится с классом `bleed-x` (`margin-left/right: -6mm`,
`preview_html._CSS_TEMPLATE`): левая и правая линии таблицы совпадают с линиями
рамки. Замерено в QtWebEngine: ширина таблицы 185.0 мм, смещение от левой и
правой линии рамки — 0.0 мм. Та же геометрия у таблицы содержания
(`models.TOC_WIDTHS` = 95 / 50 / 40 мм — Наименование | Обозначение | Листы;
сумма те же 185 мм, класс `bleed-x`, `table-layout: fixed`).

**Кэш перечня по контрольной сумме файлов.** Чтение штампов сотен страниц —
самая дорогая часть построения перечня, поэтому результат кэшируется
(`preview_html._SHEETLIST_CACHE`). Ключ кэша — «состояние» каждого PDF-файла
раздела (путь, размер и md5 первых/последних 4 КБ — читаются только края
файла, а не весь файл), плюс области штампа, шаблон обозначения и шифр.
Перечень перестраивается только когда листы графической части действительно
изменились; смена настроек тоже инвалидирует кэш. Сброс вручную —
`preview_html.clear_sheetlist_cache()`.

**Excel без сторонних библиотек.** openpyxl в проект не входит (vendor/ собран
под другой набор зависимостей), поэтому `.xlsx` читается напрямую — это ZIP с
XML: `app/core/xlsx_reader.py` разбирает `workbook.xml` (имена листов),
`sharedStrings.xml` (пул строк) и `worksheets/sheetN.xml` (ячейки). Первая
непустая строка считается шапкой и пропускается, полностью пустые строки
отбрасываются. Если файл не найден или пуст — строки строятся по листам
раздела (фолбэк), в настройках об этом выводится подсказка.

**Вставка и нумерация.** Лист идёт ПЕРВЫМ листом раздела и учитывается в
`toc.build_layout` отдельной позицией («Графическая часть. Перечень листов»),
поэтому сквозные номера, квадрат нумерации, содержание и графа «Листов»
остаются согласованными. Во всех трёх выводах лист строится по одному правилу:

- **предпросмотр / собранный HTML** — `render_graphic_sheet_list`
  (`_sheet_fragment("graphic_list", …)`), штамп формы 3;
- **Word (DOCX)** — `docx_exporter._add_graphic_sheet_list` в ОТДЕЛЬНОЙ секции
  со своим колонтитулом формы 3; документы графики идут следующей секцией без
  колонтитула (у них собственный штамп на листе);
- **PDF** — `pdf_builder._graphic_sheet_list_pdf`: страница A4 с рамкой и
  штампом формы 3, первой страницей графического сегмента.

Настройка — в контекстной панели справа при выборе раздела «Графическая
часть» (`app/ui/section_settings_form.py`).

### Лист «Состав проектной документации»

> **Статус: реализовано в HTML-предпросмотре.** Раздел идёт **вторым листом
> тома**: содержание — лист 1, состав — лист 2. Листы с рамкой и основной
> надписью **формы 5** (первый лист) и **формы 6** (последующие), на листе —
> надпись «Состав проектной документации» и таблица томов.

| Что | Как |
|-----|-----|
| Место в томе | `models.default_structure()`: сразу после «Содержания»; у старых проектов раздел вставляется при загрузке (`VolumeProject.from_dict`) |
| Колонки | Номер тома 15 / Обозначение 60 / Наименование 90 / Примечание 20 мм (`models.COMPOSITION_COLS` / `COMPOSITION_LABELS` / `COMPOSITION_WIDTHS`, сумма 185 мм = ширина между линиями рамки) |
| Высота шапки / строки | 15 мм / 8 мм (`models.COMPOSITION_HEAD_MM` / `COMPOSITION_ROW_MM`) |
| Строки | `project.composition.rows` — список словарей по `COMPOSITION_COLS` |
| Заполнение | Вручную в форме раздела (`app/ui/composition_form.py`) либо импортом из `.xlsx` |
| Доп. обозначение | `project.section_codes["composition"]` — поле «Обозначение раздела» в форме раздела; по умолчанию пустое |
| Импорт Excel | `xlsx_reader.read_composition_rows` — 4 колонки, первая непустая строка считается шапкой и пропускается |
| Единый источник строк | `models.composition_rows(project)` |
| Разбиение на листы | `preview_html.composition_rows_per_sheet` / `composition_pages` |
| Штамп | `render_composition` → `_stamp_html(2 …)` для первого листа, `_stamp_html("2a" …)` для последующих |
| Независимость штампа | `models.STAMP_SIG_INDEPENDENT` — строки подписей состава хранятся под своим ключом и НЕ связаны с общими штампами тома |

**Надпись над таблицей.** Над таблицей печатается надпись «Состав проектной
документации» (`preview_html.COMPOSITION_TITLE`), на неё отводится
`COMPOSITION_TITLE_MM` = 12 мм, которые вычитаются из области под таблицу.
По ширине таблица упирается в линии рамки (`bleed-x`), верхний внутренний отступ
снимается классом `bleed-top`. Область считается от `TEXT_TOP_INDENT_MM` (17 мм —
низ квадрата нумерации) до штампа с зазором 2 мм: **25 строк на первом листе**
(форма 5, 40 мм) и **28 — на последующих** (форма 6, 15 мм). Замер в QtWebEngine:
колонки 15 / 60 / 90 / 20 мм, шапка 15 мм, строки 8 мм, смещение таблицы от линий
рамки — 0.13 мм.

**Пустая таблица всё равно занимает лист** — на листе печатается шапка, чтобы
раздел был виден в томе и его можно было заполнить. Лист учитывается в
`toc.build_layout` отдельной позицией, поэтому сквозные номера, квадрат
нумерации и графа «Листов» остаются согласованными.

**Порядок экспорта.** HTML-предпросмотр и собранный HTML-том строят листы
раздела по одному правилу. Word собирает раздел в `docx_exporter._add_composition`
(отдельная секция, формы 5/6). В `pdf_builder` раздел пока не проведён — это
следующий шаг вместе с PDF-сборкой.

- **Справа** — **контекстная панель настроек**: показывает настройки, относящиеся к выбранному пункту. Вкладки-формы **удалены**; вместо них — стек контекстных форм. Реквизиты тома и реестр подписантов вынесены в кнопки «Реквизиты тома…» и «Подписанты…», открывающие модальные окна.

### Контекстная панель настроек (справа)

Вместо вкладок панель показывает форму, соответствующую выбранному пункту дерева:
| Выбранный пункт | Что отображается |
|-----------------|------------------|
| Обложка / Титульный лист | Настройка одного листа: на «Обложке» — группа обложки, на «Титульном листе» — группа титула (авто по ГОСТ / кастомный шаблон). Вторая группа скрыта |
| Содержание | «Обозначение раздела»: дополнительное обозначение (по умолчанию `.С`) и его итоговое значение |
| Пояснительная записка / Графическая часть | «Обозначение раздела» (`.ПЗ` / `.ГЧ`) + блок «Документы раздела» (список файлов и «Добавить документ…») |
| Приложения (раздел) | Список приложений (добавить/изменить/удалить) |
| Лист регистрации изменений | Журнал изменений |
| Документ или приложение (пункт) | Одна форма свойств элемента: файл, листы; у приложения дополнительно номер и наименование, у документа — кнопка «Редактировать ПЗ…» |

**Основных реквизитов на листах нет.** Организация, обозначение тома, объект, стадия, город, год, графа 9 и оглавление записки — свойства тома, а не листа, поэтому они не занимают контекстную панель: их редактируют кнопкой **«Реквизиты тома…»** (модальное окно, `app/ui/context_panel.py::RequisitesDialog`) либо прямо в полях предпросмотра.

**Форма реквизитов создаётся в одном экземпляре** и используется и в окне реквизитов, и для синхронизации с инлайн-правками предпросмотра.

**Отметка «включать в сборку» доступна во всех местах, где документ добавляется** — везде меняется один признак модели `needed`, поэтому состояние согласовано между ними:

| Где | Элемент управления |
|-----|--------------------|
| Дерево «Листы тома» | флажок у раздела тома |
| Свойства документа/приложения (панель справа) | флажок «Включать в сборку» |
| «Документы раздела» (ПЗ / Графика) | список документов с флажками |
| «Приложения» (таблица) | колонка «В сборку» с флажком |

Исключённый элемент **не удаляется**: он остаётся в дереве и в списках (показан серым), поэтому флажок можно вернуть. Документы, исключённые из сборки, видны и в дереве, и в списке раздела — иначе снятие флажка было бы необратимым.

**Убрать документ из проекта совсем** — кнопка «Убрать из проекта» в блоке «Документы раздела» (ПЗ и графическая часть) и кнопка «Удалить» в дереве и в таблице приложений. Удаляется запись из проекта (`project.documents` / `project.appendices`), **файл на диске не трогается**; действие подтверждается, так как необратимо (вернуть можно только повторным добавлением). В списке раздела можно выделить несколько документов сразу. Если удалённый документ был открыт в предпросмотре, окно переключается на раздел, к которому он относился (`main_window._current_object_alive`).

**Раздел без включённых документов не занимает лист** в томе и не попадает в содержание (`toc.build_layout`): иначе после снятия флажка у единственного документа ПЗ в томе оставался бы пустой лист-заглушка. Предпросмотр раздела в этом случае показывает лист-подсказку «Включите документ флажком «В сборку»».

**Путь к файлу** — поле только для чтения и кнопка выбора (общее устройство `app/ui/common.py::FileRow`, используется также для логотипа графы 9, шаблонов обложки/титула и подписи подписанта). Выбор файла пересчитывает число листов.

**Реестры** («Изменения», «Приложения», «Подписанты») построены на общем каркасе `app/ui/common.py::TableCrudForm` — таблица и кнопки «Добавить / Изменить / Удалить».

Пока идёт ввод, обновляется только подпись «Обозначение» (`section_settings_form._on_code_typing`); запись в модель и сигнал `changed` — в `_on_code_committed`, и только если значение реально изменилось (повторный уход фокуса без правок предпросмотр не трогает). Так же сохраняются шаблон обозначения листа и путь к книге Excel перечня;
- графа «Обозначение» в штампе показывает составное значение, но инлайн-правка этой ячейки записывает в модель только обозначение тома — код раздела отбрасывается (`main_window._strip_section_code`).

**Открытый раздел и вид предпросмотра сохраняются.** После правки настроек перерисовка должна оставлять пользователя там же:

- дерево восстанавливает подсветку выбранного раздела (`sheet_tree._refresh` запоминает выбор ДО `clear()`, `_restore_selection` ставит его с заблокированными сигналами — иначе повторный выбор запускал лишнюю перерисовку и заново заполнял контекстную форму);

При реальном переходе на другой лист по-прежнему выполняется «вписать в окно» с началом листа.

**Реквизиты тома** — кнопка «Реквизиты тома…» в верхней части панели: основные реквизиты, графа 9 (текст/логотип) и автоматическое оглавление записки. Изменения применяются по «OK».

**Подписанты** — кнопка «Подписанты…»: модальное окно редактирования реестра подписантов (добавить/изменить/удалить).

### Правила оформления листов (в предпросмотре и при сборке)

| Лист / раздел | Основная надпись (штамп) | Рамка |
|---------------|--------------------------|-------|
| Обложка | **без штампа** | без рамки |
| Титульный лист | **без штампа** | без рамки |
| Содержание тома | **форма 5** | есть |
| Состав проектной документации | **первый лист — форма 5, последующие — форма 6** | есть |
| Оглавление ПЗ (авто) | **первый лист — форма 5, последующие — форма 6** | есть |
| Пояснительная записка | **первый лист — форма 5, последующие — форма 6** | есть |
| Графическая часть | **вставляется без штампа** (лист из CAD) | без рамки |
| Приложения | **вставляются без штампа** (самостоятельный документ) | без рамки |

> **В Word — иначе.** Первый лист текстовых разделов (содержание, состав ПД,
> оглавление и листы ПЗ, лист регистрации изменений) выводится формой 3,
> последующие — формой 6 (`gost.FORM_TEXT_FIRST_WORD`, см. §4.8). Таблица выше
> описывает предпросмотр, HTML и PDF: там остаётся форма 5.

- **Масштаб при предпросмотре** — по умолчанию лист **вписывается под размер окна** (автоподгонка `fit-to-window`). Кнопка «Вписать в окно» и ±зум остаются доступными.

**Графическая часть вписывается по ПЕРВОМУ листу** (`PreviewWidget._fit_first`).
Масштаб считается по первому листу раздела — это лист «Графическая часть» с
перечнем (A4). Чертёжные листы (A1/A2) в разы больше, и масштаб по самому
большому листу делал перечень нечитаемо мелким: при окне 900×1200 px было 36 %,
стало 95 % — перечень крупнее в 2.7 раза и виден целиком. Остальные листы
раздела листаются прокруткой; кнопка «Вписать в окно» использует то же правило.
Для записки и приложений правило прежнее — по самому широкому и высокому листу.
- **Сборка — пункт строки меню, а не подменю.** «Сборка» в строке меню — это команда (`QAction` без меню, сочетание **Ctrl+B**): нажатие сразу открывает **мини-окно сборки** (`app/ui/build_dialog.py`) с флажками «PDF (\*.pdf)», «DOC — Word (\*.docx)», «HTML (\*.html)» и кнопками **«Собрать»** / **«Отмена»**. Промежуточного подменю с единственным пунктом «Собрать том…» больше нет. Пока не отмечен ни один формат, «Собрать» неактивна. «Отмена» отменяет всю сборку — ни файлов, ни preflight. Набор хранится в `config.json` (`Config.build_formats`, ключи `pdf` / `docx` / `html`) и восстанавливается при следующем открытии окна.

  **Код результата диалога берётся у класса.** `QDialog.Accepted` — атрибут класса: у экземпляра диалога `dlg.Accepted` не существует, и обращение к нему даёт `AttributeError`. В слоте Qt такой сбой молча обрывает обработчик — окно закрывалось, а сборка не начиналась (нажатие «Собрать» «ничего не делало»). Сравнивать нужно `dlg.exec() != QDialog.Accepted` (`main_window._ask_build_formats`, `context_panel._open_requisites`).

  **Пустой список форматов означает «ничего не отмечено».** `BuildDialog(selected=None)` — набор не задан, отмечаются все форматы; `selected=[]` — ни один флажок не стоит, и «Собрать» неактивна. Раньше пустой список трактовался как «не задано», и все форматы включались.
- **Сборка тома** — «Сборка → Собрать том…»: окно форматов → preflight → имя файла (фильтр — по отмеченным форматам) → сборка рядом с этим именем:
  - **HTML** (`build_volume_html`) собирается **первым**;
  - **PDF** печатается **из готового HTML** (`html_export.html_file_to_pdf` → QtWebEngine): вёрстка, номера листов и штампы те же, что в предпросмотре. Листы графической части с `data-pdf-src` вставляются вектором из исходного файла, остальные — печатью HTML. **Из DOCX PDF больше не собирается** (`build_full_pdf` в сборке тома не используется);
  - **DOCX** (`build_text_docx`) — сгенерированные листы + текст ПЗ из исходных DOCX; страницы исходных PDF в Word не выводятся. Флажок **«DOC — по разделам (отдельные файлы)»** (`build_chapters_docx`) пишет каждый раздел тома в свой `.docx`: спрашивается каталог, файлы именуются обозначением раздела («02-2026-ТР.ТП Пояснительная записка.docx»). Флажок хранится в `config.json` (`Config.build_docx_chapters`) и активен только при отмеченном DOCX.

  При сборке показывается компактное стилизованное окно прогресса с текущим этапом. HTML и DOCX формируются в фоновом потоке, PDF — в GUI-потоке через QtWebEngine с отображением номера листа и процента готовности. Сбой одного формата не отменяет остальные: итоговый диалог показывает, что собрано и что не удалось. В начало пояснительной записки автоматически вставляется **оглавление по уровням заголовков DOCX** (см. §«Автоматическое оглавление пояснительной записки»).

  **DOCX: нумерация и разбиение страниц.** Не включать `w:updateFields` на весь документ: DOCX экспортируется с `w:updateFields=false`, а внешние связи при сборке не переносятся. Графа «Листов» получает количество из `toc.build_layout`; номер «Лист» и квадрат сквозной нумерации остаются полями Word, перезапускаемыми и смещаемыми в пределах секции. Разрывы страниц ПЗ используют `_paginate_docx`: обычные абзацы сохраняют порядок, но не учитываются в расчёте бюджета страниц и могут свободно переходить на следующий лист; расчёт планирует только таблицы и явные разрывы, заданные в исходнике. Таблицы делятся по строкам с повторением шапки; строки таблиц не разрываются (`w:cantSplit`). Отступы и межстрочный интервал ячеек выровнены с CSS, исходное выравнивание ячеек читается из Word и применяется в обоих выводах. Квадрат сквозного номера центрируется по горизонтали и вертикали; изображения подписей в Word используют `_signature_pixmap` с обрезкой росчерка и прозрачным фоном.

  **Имя файла сборки по умолчанию** — обозначение тома и дата: `обозначение_тома_ГГ_ММ_ДД`, например `02-2026-ТР_26_11_24`. Если обозначение не заполнено, используется `том`.
- **Точный размер листа в PDF из HTML.** Chromium печатает страницу на доли миллиметра меньше заданного размера (A4 → 209.9 × 297.0 мм), из-за чего правая линия рамки уходила от края листа. Размер выставляется точно по медиабоксу после печати (`html_export._fix_page_size`), содержимое не масштабируется: замер готового файла — **210.0 × 297.0 мм** на каждой странице.
- **Пустой раздел листа не занимает.** Раздел без включённых документов не даёт листа и в HTML/PDF: лист «Графическая часть» с перечнем вставляется только при наличии самих листов графики (`_section_fragments`), ПЗ без документов в текстовый DOCX не попадает (`build_text_docx` отфильтровывает пустые разделы). Так в томе не остаётся одиноких листов с одним штампом.
- **Сборка в HTML** — `build_volume_html` собирает весь том в **единый HTML-файл** (листы идут подряд, при печати — с разрывом страницы). Готовый файл можно открыть в браузере.
- **Геометрия основной надписи** — единый источник `app/core/geometry.py`: сетки форм 3/5/6 (разбивка колонок, высоты строк), согласованные с образцами Форма 3/5/6.pdf и HTML-предпросмотром. Используется в Word и PDF, чтобы штампы совпадали.

#### Word рисует основную надпись той же сеткой, что предпросмотр и PDF

#### Основная надпись в Word: кегль подбирается по ширине графы

> **Статус: реализовано.** Графы штампа узкие (10–20 мм), а значения в них при
> штатном кегле 10–12 pt шире графы: «Стадия» — 12.3 мм при 12 pt, «17.11.26» —
> 9.6 мм при 10 pt, «Кол.уч» — 8.9 мм при 10 pt. Word кегль не уменьшает, поэтому
> текст переносился («Стади/я», «17.11/.26»), высоты строк (`atLeast`) росли и
> штамп **разъезжался вдвое**: форма 5 занимала 82 мм вместо 40 и наезжала на
> текст листа.

- Ширина текста измеряется по **файлу шрифта** (`app/core/textfit.py`, метрики
  глифов через PyMuPDF), поэтому подобранный кегль совпадает с тем, что видит
  Word. Без файла шрифта используется консервативная оценка.
- Перед заполнением ячейки кегль уменьшается до первого, при котором строка
  влезает в графу (шаг 0.5 pt, запас 0.3 мм).
- Внутренние отступы ячеек обнулены (`docx_tables.set_table_cell_margins`):
  по умолчанию Word оставляет 1.9 мм с каждой стороны, и в графе 10 мм на текст
  оставалось 6.2 мм.
- Перенос в графах запрещён (`set_cell_no_wrap`), высоты строк задаются правилом
  **exact** — строка не может вырасти, геометрия штампа всегда равна сетке.
- Абзацы в графах получают нулевые отбивки и одинарный интервал
  (`docx_exporter._tight_paragraph`): стиль Normal добавлял отбивку и межстрочный
  1.08, что выталкивало текст за сетку.

#### Рамка листа, отступы и разбиение на листы в Word

- Рамка привязана к **границе текста** (`w:pgBorders`, `offsetFrom="text"`, все
  `w:space` = 0), а поля заданы по линиям рамки: 20 мм слева, по 5 мм с других
  сторон. Замер в Word: линии проходят **x = 19.7…205.1 мм, y = 4.7…292.1 мм**,
  то есть ровно по сетке ГОСТ.
  Привязка к краю листа (`offsetFrom="page"`) для этой задачи не годится: Word
  ограничивает отступ рамки 31 pt (≈11 мм), поэтому левая линия вставала на
  8.8 мм вместо 20 мм и не совпадала с таблицей.
- Штамп прижат к нижней линии рамки: расстояние колонтитула равно нижнему полю
  (5 мм). Низ штампа и низ рамки совпадают (y = 292 мм при A4).
- **Внутренний отступ текста 6 мм — как `padding` у `.sheet-content`.** Замер
  эталонного HTML-тома: текст начинается на **x = 26 мм** (20 рамка + 6) и
  **y = 23 мм** (17 зона квадрата нумерации + 6). В Word этот отступ задаётся не
  полями (они сдвинули бы рамку), а:
  - сверху — пустым абзацем верхнего колонтитула (`_set_top_indent`): высота =
    23 − 5 (расстояние колонтитула) = 18 мм;
  - слева/справа — отступами абзацев (`_apply_sheet_indent`) и центрированием
    таблиц.
- **Таблицы выравниваются по центру** (`docx_tables.set_table_center`,
  `w:jc = center`). Текстовая область совпадает с внутренней областью рамки,
  поэтому таблица на всю ширину (185 мм: содержание, состав ПД, перечень листов,
  лист изменений) встаёт линиями ровно по рамке — замер **x = 19.9…204.9**.
  Таблицы ПЗ нормируются на 173 мм (185 − 2 × 6) и встают с равными полями
  **x = 25.9…198.9** — как в HTML (26.0). Подбор `w:tblInd` не годится: Word
  выводит таблицу с отрицательным отступом на величину отступа ячейки, и таблица
  заходила за рамку (x = 17.9).
- **Границы таблиц задаются на уровне таблицы** (`set_table_borders`,
  `w:tblBorders`). Границы отдельных ячеек терялись у объединённых, и в таблицах
  отсутствовала часть линий — при полной сетке в HTML.
- **Сетка формы 6 — два ряда значений таблицы изменений** (`geometry.form6_cells`:
  y 5..10 и 10..15). Раньше оба ряда были одной объединённой ячейкой, и линия на
  10 мм в Word исчезала: 4 горизонтали вместо 5 в HTML.
- **«Продолжение таблицы» — строка ВНУТРИ таблицы** (как `.dt-cont` в HTML), а не
  отдельный абзац: отдельным абзацем она занимала больше высоты, и на лист
  влезало меньше строк.
- **Нижняя граница текста — по самому малому штампу раздела.** Нижнее поле в
  Word задаётся на секцию, а штампы разные (форма 5 — 40 мм). Резерв считается по
  форме 6 (15 мм): тогда область Word не меньше бюджета пагинации, и Word не
  добавляет своих разрывов.
- **Разбиение на листы берётся из предпросмотра.** `_add_pz_doc` вызывает
  `preview_html._paginate_docx` — ту же функцию, что строит листы HTML, — и
  ставит разрыв страницы там же, где в предпросмотре начинается новый лист.
- **Переносы строк считаются по метрикам шрифта** (`textfit.visual_lines`,
  ширина слов из файла TTF). Оценка «знаков в строке» (81 знак при 12 pt)
  совпадала только на коротких словах: длинное слово
  («санитарно-эпидемиологические», «встроенно-пристроенный») в колонку не
  влезает целиком, Word переносит его раньше — и строк выходило больше, чем
  предсказывала модель. Точность проверена тестом из 10 абзацев: **10 из 10
  совпадений** с Word. В `_paragraph_lines` учитываются отступы абзаца и
  «красная строка» (первая строка уже остальных), в `_estimate_table_row_h` —
  ширина ячейки минус внутренние отступы.
- **Высота строки — 5.56 мм при 12 pt** (`preview_html._LINE_H_MM`, замер по
  собранному тому: 12 pt → 5.56, 14 pt → 6.35). Раньше стояло 0.5 × кегль
  (6.0 мм при 12 pt) — абзацы выходили на 8 % выше, и пагинация расходилась с
  вёрсткой.
- **Высота абзаца в Word приводится к предпросмотру**
  (`docx_exporter._align_paragraph_metrics`): если в исходнике задан точный
  межстрочный (`w:spacing line`), он используется буквально (18 pt → 6.35 мм, как
  в HTML); иначе берётся `_line_height` из предпросмотра. Отбивки задаются явно
  (0 при отсутствии в исходнике): стиль Normal (1.08 + 8 pt) делал каждый абзац
  выше и Word рвал страницу там, где в предпросмотре разрыва нет.
- **Заголовок не отрывается от следующего абзаца**: в модели пагинации
  (`keep_with_next`) и в Word (`paragraph_format.keep_with_next`). Иначе Word
  оставлял заголовок в конце листа, а модель переносила его — разрывы
  расходились.
- **Бюджет листа совпадает у модели и Word:** 246 мм на листе с формой 6.
  Нижнее поле = 5 + штамп + 2 + 6 = 28 мм, текст начинается на 23 мм, значит
  доступно 297 − 28 − 23 = 246 мм — столько же, сколько вычитает
  `_page_text_height`. Плюс 6 мм отступа снизу НЕ добавляются.
- **Строки таблиц — правило `exact`.** При `atLeast` строка росла от переносов,
  таблица не влезала на лист, Word разрывал её сам, и наш разрыв давал **пустой
  лист**. Кегль текста в ячейке подбирается под ширину графы (`_fit_cell_run`),
  поэтому наименование остаётся одной строкой и геометрия сетки сохраняется.
- **Разрыв между оглавлением и запиской** ставится отдельно: листы оглавления и
  ПЗ в предпросмотре раздельные.

- **Надёжный экспорт полного тома в PDF** — сборка PDF **не зависит от Word COM**: если Word недоступен, текстовая часть собирается через PyMuPDF с кириллицей (шрифт ISOCPEUR), графика/приложения вставляются как есть. Проверка доступности Word выполняется с таймаутом (`word_com.word_available`), чтобы не зависнуть.
- **Загрузка файла выделенной части** — в свойствах документа/приложения (панель справа) есть кнопка «Выбрать файл…»: заменяет путь к исходному файлу и пересчитывает число листов.
- **Нечитаемый исходник не роняет сборку.** Preflight (`app/core/preflight.py`) открывает включённые DOCX через `python-docx` и PDF через `PyMuPDF`: файл, который существует, но не открывается (битый, или старый `.doc` под именем `.docx`), даёт **ошибку с причиной** и блокирует экспорт. Если такой файл всё же попал в сборку, лист выводится **заглушкой** (`preview_html._placeholder_sheet_fragment`) — она не обращается к исходнику и поэтому не может зациклиться. Раньше возврат из загрузчика в `_sheet_fragment` давал бесконечную рекурсию `_sheet_fragment → _docx_sheet_fragments → _sheet_fragment` и ошибку «maximum recursion depth exceeded» при сборке тома в HTML.
- **Ошибки сборки логируются.** «Собрать том в HTML» при падении пишет traceback в `tmp/build.log` и показывает путь к логу в диалоге (`main_window._log_build_error`).
- **Текст в «надписях» Word читается.** Типовые записки верстают текст в фигурах Word — он лежит в `w:txbxContent` (VML `v:textbox` и DrawingML `wps:txbx`), а `python-docx` в `paragraph.runs` его не отдаёт. `docx_reader._textbox_paragraphs` извлекает такие абзацы и ставит им признак `from_textbox`: они **выводятся**, но **не адресуются для правок** (`para_index = -1`), иначе правка записалась бы в чужой абзац файла и сдвинула бы адреса всех последующих.
- **Пустой документ объясняется, а не молчит.** Если DOCX прочитан, но в нём нет ни текста, ни таблиц (`DocxContent.is_empty`), вместо пустого листа выводится заглушка с причиной (`_empty_docx_note`: текст в надписях/фигурах, только рисунки, колонтитулы, сноски). Preflight при этом даёт предупреждение до сборки, а при тексте в надписях — отдельное предупреждение о том, что правка в предпросмотре к нему не применяется.
- **Сбой разбора DOCX не скрывает записку.** Разбор устойчив поабзацно (`docx_reader._read_paragraph`): неизвестный стиль или битый элемент портят только свой абзац, остальные читаются. Если обычный разбор всё же упал, текст извлекается аварийно прямо из `word/document.xml` (`docx_reader.simple_docx_content` — абзацы и таблицы, без тонкого оформления), поэтому в предпросмотре видна записка, а не заглушка. Заглушка остаётся только когда не читается вообще ничего, и тогда **называет причину** с типом ошибки.
- **Сбой предпросмотра не маскируется заглушкой.** Раньше `preview_widget._build_html` любое исключение при построении листов молча подменял листом «Не удалось отобразить содержимое файла», и причину нельзя было узнать по экрану. Теперь на листе выводится **«Сбой предпросмотра: <тип ошибки>: <сообщение>»** и путь к `tmp/build.log`, куда пишется полный traceback (`tom_builder.preview`). Пустой результат построения объясняется отдельно («не удалось получить ни одного листа»). Раздел определяется по `snapshot["section"]`, а если поля нет — по `section_label`/`label`, поэтому раздел ПЗ/графики открывается и при неполном снимке данных.
- **Геометрия форм (ГОСТ Р 21.101-2020):** форма 3 (графический лист) — **185×55 мм**; форма 5 (первый лист текста) — **185×40 мм**; форма 6 (последующие) — **185×15 мм**. В предпросмотре формы обозначаются внутренними ключами 1 (форма 3), 2 (форма 5), «2a» (форма 6).

### Оформление абзацев и списков Word (отступы, интервалы)

> **Статус: реализовано.** Оформление абзацев исходного DOCX переносится в **все**
> выводы — предпросмотр, «Собрать том/раздел в HTML», Word (DOCX) и PDF: абзацные
> отступы, «красная строка», интервалы до/после абзаца, межстрочный интервал,
> выравнивание и **списки** (маркированные и нумерованные).

**Единый источник — `app/core/pz_format.py`.** Word описывает абзац не «сам по себе»,
а через наследование: свойства абзаца (`w:pPr`) → стиль абзаца (`w:style/w:pPr`) →
базовый стиль (`w:basedOn`) → умолчания документа (`w:docDefaults`). Списки задаются
ссылкой `w:numPr` (`numId` + `ilvl`) на определение в `word/numbering.xml`, причём
номер, формат и отступы уровня тоже могут приходить из стиля. Модуль собирает эту
цепочку в `ParagraphFormat` (миллиметры и пункты), поэтому предпросмотр и экспорт
показывают одно и то же:

| Что берётся из Word | Как переносится |
|---------------------|-----------------|
| Отступ слева/справа (`w:ind left/right`, в т.ч. в `Chars`) | `margin-left/right` (CSS) и `left_indent` / `right_indent` (DOCX) |
| Отступ первой строки / выступ (`w:firstLine` / `w:hanging`) | `text-indent` (CSS) и `first_line_indent` (DOCX) |
| Интервалы до/после абзаца (`w:spacing before/after`, `beforeLines/afterLines`) | CSS `padding-top/bottom` — именно padding, а не margin: в Word интервалы соседних абзацев **суммируются**, а margin-ы в CSS схлопываются (важно при пустых строках) |
| Межстрочный интервал (`w:line` + `w:lineRule`) | CSS `line-height`: множитель Word × 1.15, для `exact/atleast` — точное значение в pt; в DOCX — обратный перевод |
| Выравнивание (`w:jc`) | Переносится **как в Word**; если в Word выравнивание не задано, применяется выключка по ширине (ГОСТ) |
| Разрыв страницы «с новой страницы» (`w:pageBreakBefore`) | Абзац начинает новый лист предпросмотра/сборки |
| Списки (`w:numPr` + `w:numbering`) | Маркер Word («1.», «а)», «•») выводится **отдельным боксом** в поле «висячего» отступа; номера считаются по документу |

**Абзацный отступ по умолчанию — 5 знаков.** Если Word отступ первой строки НЕ задаёт,
он подставляется при нормализации текста (`pz_format._read_formats`): один знак Word —
половина кегля, поэтому при кегле основного текста ПЗ 14 pt отступ равен
**5 × 14 × 0.5 = 35 pt = 12.35 мм** (ГОСТ: 1.25 см). Величина настраивается:

- `config.json` → `paragraph_indent_chars` (по умолчанию `5`), кегль берётся из
  настройки текста ПЗ `text_fonts.body_size` (группа «Обычный текст», см.
  «Шрифт и кегль текста ПЗ — один пункт настройки»); расчёт —
  `Config.paragraph_indent_mm()` и `pz_format.indent_mm_for_chars(chars, size_pt)`,
  поэтому при смене кегля отступ пересчитывается автоматически;
- отступ применяется к **абзацам** и не применяется к **заголовкам** (по ГОСТ они
  центрируются) и к **пунктам списков** (у них своя геометрия `left + hanging`, и
  «красная строка» сдвинула бы текст пункта относительно маркера);
- явно заданный в Word отступ (`w:firstLine` / `w:hanging`) **не переопределяется**;
- отступ выводится во всех выводах: CSS `text-indent` в предпросмотре и собранном HTML,
  `first_line_indent` в DOCX, сдвиг первой строки в PDF (в т.ч. в запасном пути без Word).

**Списки.** Тип списка (маркированный/нумерованный), формат номера
(`decimal`, `lowerLetter`, `lowerRoman`, …), шаблон маркера (`w:lvlText`: «%1.», «а)»,
«•»), отступ уровня и его выравнивание (`w:lvlJc`) берутся из `numbering.xml` —
включая `w:lvlOverride` и «строчные» единицы отступов. Номера нумерованных списков
считаются по документу и совпадают с Word.

- в **HTML/PDF** маркер — отдельный бокс слева от текста пункта (в поле «висячего»
  отступа Word), поэтому текст пункта начинается ровно на своём отступе, а
  редактирование пункта в предпросмотре не затрагивает маркер;
- в **DOCX** маркер переносится текстом («1.» + табуляция), отступы — настоящими
  `w:ind left + hanging`, позиция табуляции — на уровне текста пункта. Ссылкой на
  `numbering.xml` нумерация намеренно не переносится: определение списка живёт в
  исходном пакете DOCX, и его «как есть» перенос ломается при объединении нескольких
  документов в один том.

**Что остаётся по ГОСТ, а не по Word:** шрифт и кегль текста ПЗ — из настройки
текста ПЗ (`config.TextFonts`, группы «обычный текст» / «заголовки» / «таблицы»);
из Word берётся только «геометрия» абзаца.

### Шрифт и кегль текста ПЗ — один пункт настройки

> **Статус: реализовано.** Меню **«Настройки» → «Шрифты текста ПЗ…»**
> (`app/ui/fonts_dialog.py`) задаёт шрифт и кегль для трёх групп текста
> пояснительной записки. Значения хранятся в `config.json` (`text_fonts`) и
> используются **всеми** выводами — предпросмотром, Word (DOCX) и PDF, — поэтому
> кегль и число листов в предпросмотре совпадают с собранным томом.

| Группа | Ключ | Что оформляет | По умолчанию |
|--------|------|----------------|--------------|
| Обычный текст | `body` | абзацы записки (в т.ч. пункты списков) | ISOCPEUR, 12 pt |
| Заголовки | `heading` | заголовки разделов записки | ISOCPEUR, 14 pt |
| Таблицы | `table` | ячейки таблиц DOCX в записке | ISOCPEUR, 10 pt |

**Начертание (единое правило).** Заголовок — абзац **стиля Word «Heading N» /
«Заголовок N»** (см. `pz_toc.is_heading_paragraph`); он выводится
**полужирным**, курсив берётся из исходника. Обычный текст записки печатается
**единым — без полужирного и курсива**, даже если в исходном DOCX фрагменты
выделены. Абзац без стиля заголовком не считается, поэтому полужирный шрифт
сам по себе выделения в выводе не даёт. Правило задано один раз —
`pz_toc.heading_emphasis` — и применяется в предпросмотре, Word (DOCX) и в
«нормализованной» копии, по которой Word размечает листы (`word_pagination`,
кэш раскладки от этого зависит), поэтому начертание не расходится между
выводами и разбивкой.

- в окне настроек есть **образец текста**: выбранные шрифт и кегль сразу видны,
  а если семейства нет в системе — выводится предупреждение (Word и PDF подставят
  своё начертание);
- **предпросмотр**: кегль и `font-family` абзацев выводятся инлайново, таблицы —
  через CSS (`{table_size}` / `{table_font}`); от кегля таблиц зависят и метрики
  разбивки по листам (`preview_html._table_scale`), поэтому при смене кегля
  пагинация пересчитывается вместе с отрисовкой;
- **Word (DOCX)**: `docx_exporter._add_pz_doc` ставит шрифт/кегль группы каждому
  run-у абзаца и всем runs таблиц;
- **PDF через Word COM** — кегль берётся из собранного DOCX (то же значение);
- **запасной PDF (PyMuPDF)**: шрифты групп встраиваются в каждую страницу
  (`pdf_builder._text_font_files` / `_register_group_fonts`), кегли — из настройки.
  Файл шрифта ищется по имени семейства через реестр установленных шрифтов
  (`app/core/fonts.py`); если шрифт не установлен — берётся основной ISOCPEUR;
- **абзацный отступ** (5 знаков) считается от кегля группы `body`, поэтому при
  смене кегля основного текста он пересчитывается;
- карта кеглей `FontMap` (§5) остаётся для **основной надписи, содержания,
  титула/обложки, оглавления и приложений** — это отдельные элементы оформления,
  а не текст записки.

### Автоматическое оглавление пояснительной записки

> **Статус: реализовано.** В начале пояснительной записки **автоматически**
> формируется оглавление по **уровням заголовков исходного DOCX** (Word). Оно
> вставляется **первым листом** записки в предпросмотр, Word (DOCX) и PDF;
> исходный DOCX **не изменяется**.

**Единый источник — `app/core/pz_toc.py`.** Предпросмотр, «Собрать том»,
DOCX и PDF используют одни и те же строки оглавления, поэтому наименования и
номера листов не расходятся.

| Что | Как определяется |
|-----|------------------|
| Заголовок | **только стиль Word** — «Heading N» / «Заголовок N», включая стили, созданные на основе них (`w:basedOn`), и имена стилей, содержащие «heading» (`is_heading_paragraph`). Полужирный шрифт, выравнивание по центру, длина строки и завершающая точка **не учитываются**: раньше это была эвристика, и она втягивала в оглавление формулы и подписи таблиц. Отбрасывается только абзац без текста — выводить в оглавление нечего. Других условий отбора нет: каждый абзац со стилем-заголовком даёт отдельный пункт |
| Уровень | только из стиля («Heading 2» → 2); у стиля-заголовка без номера («Заголовок») — 1. **В оглавление входят только уровни 1–3**, заголовки 4-го уровня и глубже отбрасываются (`MAX_LEVEL`) |
| Номер раздела | из самого заголовка («2.1 Наименование» → «2.1»); **номера не придумываются**. Заголовки вида «Раздел 2. Наименование» выводятся как есть |
| Наименование | текст заголовка, приведённый к одному пробелу между словами |
| Номер листа | номер листа **ПЗ** по **раскладке Word** исходного DOCX (`word_pagination.cached_docx_pages`, форма 6): оценочная пагинация давала 2 листа вместо 13, и половина заголовков получала один и тот же номер |
| Разбивка по листам | по высоте строк (кегль и line-height как у текста ПЗ); продолжение — на следующих листах записки |

**Нормализация текста (требование к пояснительной записке):**

- при сопоставлении и нормализации текста **не учитываются пробелы** — обычные,
  неразрывные (NBSP), узкие, табуляции, BOM (`normalize_text` / `clean_text`);
- **не учитывается перенос текста на другую страницу Word**: разрыв страницы
  (`w:pageBreakBefore`, `w:br type="page"`) не создаёт новый заголовок и не
  «склеивает» разные — абзац-заголовок остаётся одним пунктом оглавления, а
  пустые абзацы, строки из пробелов и символы разрыва заголовками не считаются
  и в оглавление не попадают;
- перенос строки (`w:br`) внутри абзаца не разрывает пункт: «Содержание   раздела»
  выводится как «Содержание раздела».

**Оформление строки оглавления:** «номер — наименование — отточие — номер листа».
Строки выводятся **шрифтом и кеглем обычного текста записки** (группа `body`
из `config.TextFonts`), без полужирного; строки начинаются с внутреннего отступа
листа (`SHEET_PAD_MM` = 6 мм), поэтому номер листа стоит у правого края текста.

**Отступ по уровням — один символ.** Строка 2-го уровня сдвинута вправо на
**один символ** относительно 1-го, строка 3-го — ещё на один символ относительно
2-го (`pz_toc.level_indent_mm`). Ширина символа берётся из файла шрифта
оглавления при его кегле (метрики `textfit`), поэтому отступ масштабируется
вместе с настройкой шрифта текста ПЗ: при ISOCPEUR 12 pt это 1,91 мм на уровень.
Если метрик шрифта нет — запасное значение `LEVEL_INDENT_MM` = 2,2 мм.

- **Word (DOCX):** отточие — **правая табуляция с заполнителем DOTS**
  (`w:tab w:val="right" w:leader="dot"`, позиция `DOCX_TAB_POS_MM` = 179 мм —
  185 мм рамки минус 6 мм отступа — минус отступ уровня), поэтому номер листа
  стоит у правого края текстовой области, а промежуток заполнен точками;
- **HTML-предпросмотр и «Собрать в HTML»:** отточие — точечная нижняя граница
  «резинки» между текстом и номером (flex-строка), номер — справа;
- **PDF через Word COM:** как в DOCX; **PDF запасным путём (PyMuPDF, без Word):**
  отточие выводится точками.

**Гиперссылки на листы.** Наименование каждой строки — ссылка на свой заголовок
в записке:

- в **DOCX** заголовок получает закладку `MIMO_H{индекс абзаца}`
  (`w:bookmarkStart`), а строка оглавления — внутреннюю гиперссылку
  (`w:hyperlink w:anchor=...`) с тем же текстом и оформлением, что и раньше
  (цвет и подчёркивание не добавляются). Закладки ставятся только в том
  документе, по которому построено оглавление (`toc_source`);
- в **HTML** абзацу-заголовку ставится `id="MIMO_H{индекс}"` (только первому
  фрагменту разрезанного листом абзаца), строка оглавления — `<a href="#MIMO_H…">`;
- имена якорей — `pz_toc.heading_anchor` / `anchor_map` (единый источник).

**Настройка:** флажок **«Автоматическое оглавление по уровням текста из Word»**
в форме реквизитов (панель справа); хранится в конфигурации оформления — ключ
`toc_enabled` (`config.json`, по умолчанию `true`). Файла конфигурации может не
быть — тогда действуют значения по умолчанию, **оглавление включено**.

**Кегли оглавления.** Заголовок листа «ОГЛАВЛЕНИЕ» — из карты кеглей
(`config.FontMap`, `content_header`, 14 pt); строки — **кегль и шрифт обычного
текста записки** (группа `body` из `config.TextFonts`, см. выше), а не `toc_row`:
раньше строки шли кеглем `toc_row`, и оглавление выбивалось из текста записки.

**Нумерация.** Листы оглавления входят в нумерацию раздела ПЗ и в «Листов M»
(учитываются в `app.core.toc.build_layout`, в содержании тома и в предпросмотре).
Большой штамп (форма 5) несёт первый лист записки — им становится лист
оглавления; листы самой записки — последующие (форма 6).

Номера листов в строках оглавления — **как внизу листа**, то есть по графе
«Лист» штампа: нумерация ведётся **внутри раздела ПЗ**, без сквозной нумерации
тома. От того, каким по счёту идёт раздел ПЗ в томе, номера не зависят: при
сборке отдельного раздела и при сборке тома они одинаковы.

В **Word (DOCX)** номер строки — не литеральное число, а **поле
`PAGEREF`** на закладку заголовка (`{ PAGEREF MIMO_H123 \h }`), поэтому Word
подставляет номер того листа, где заголовок оказался в собранном файле. Это
принципиально: раскладка исходной записки и собранного раздела **разная** —
оформленные таблицы, отступы и штампы занимают больше места, и любое число,
посчитанное заранее, отставало от настоящего листа (расхождение до 2 листов).
Поле пересчитывается при открытии документа (`w:updateFields`), при показе
листов в предпросмотре и перед экспортом в PDF, поэтому напечатанный номер
всегда совпадает с графой «Лист». Кэшированное значение поля — оценка по
раскладке исходника: её видно только в программах, которые не считают поля.

> **Стили заголовков сохраняются.** Абзацы-заголовки в собранном DOCX получают
> стиль исходника (`Заголовок 1/2/3`, `docx_exporter._apply_heading_style`),
> хотя оформление задаётся наше — шрифт, кегль, отступы и интервалы
> проставляются явно и перекрывают параметры стиля шаблона. Благодаря этому
> Word видит структуру документа: работает навигация по заголовкам и
> обновление поля оглавления, если его вставят вручную.
>
> **И сам стиль приводится к общему оформлению** (`_normalize_style_fonts`).
> Стили `Heading 1…3` шаблона python-docx несут шрифт темы (`majorHAnsi`) и
> синий цвет акцента (`365F91`), поэтому текст, набранный в Word поверх
> заголовка, снова становился бы синим. У стиля удаляются тематические ссылки
> шрифта и цвета, ставится шрифт из настроек и цвет `auto`. Прямое оформление
> run-ов и оформление стиля совпадают, поэтому шрифт и цвет заголовков не
> возвращаются к исходнику ни при сборке, ни при правке.

> **Размещение и принадлежность.** Оглавление принадлежит записке целиком и
> показывается только перед её **первым** документом; при нескольких DOCX в
> разделе ПЗ (или при открытии второго документа в предпросмотре) лист
> оглавления не повторяется.

**Когда оглавление не выводится:** в разделе ПЗ нет DOCX; оглавление выключено
в конфигурации; в документе не найдено ни одного заголовка (лист-«пустышка» с
одной шапкой не создаётся); или раздел «Пояснительная записка» исключён из
структуры тома.

**Разбивка на листы.** Границы листов задаёт **Word**: раскладка снимается с
«нормализованной» копии DOCX (`word_pagination.cached_docx_pages`, кэш
`<файл>.pagination/`) и используется предпросмотром, оглавлением, содержанием
(«Листов M») и сборкой — поэтому число листов всюду одинаковое. Оценочная высота
абзаца (`preview_html._estimate_paragraph_h`) работает только как запасной путь,
когда Word недоступен. Разметка правки (`contenteditable`,
`data-para-index`) есть **только** в интерактивном предпросмотре: в собранных
HTML/PDF выводится чистый `<p>` без `data-` атрибутов.

**Запись правок.** Enter в абзаце ПЗ вставляет **мягкий перенос** (`<br>`) — так же,
как Shift+Enter в Word; при сохранении такой текст раскладывается по абзацам
(`app/core/docx_edit.py`), поэтому ручное разбиение строки не теряется.

**Перелив текста по листам в HTML отсутствует.** Разбивка на листы считается
**только в Word** (`app/core/word_pagination.py`): предпросмотр раскладывает
блоки строго по номерам страниц из разметки и **не переливает** их между
листами. Раньше браузерный перелив двигал блоки по своему усмотрению и
расходился с Word (например, слово «коммуникаций» оставалось внизу листа,
хотя Word перенёс его на следующий), поэтому перелив удалён.

| Что происходит | Как |
|----------------|-----|
| Границы листов | Задаёт Word; `_paginate_docx` группирует блоки по `fragments` разметки |
| Разрез абзаца Word между листами | Смещение из Word уже стоит между словами — разрез остаётся там символ в символ (`_split_text_at_word_boundaries`). Если смещение попало внутрь слова, разрез откатывается к началу слова, а не дотягивается до его конца |
| Правка разрезанного абзаца | В Python уходит текст **всех частей** (`joinParts`), поэтому в DOCX по-прежнему один абзац и правка не расходится |
| Правка текста в предпросмотре | Python помечает разметку устаревшей и запускает новый расчёт листов в Word (`_mark_pagination_stale`) |

Разбивка **самой сборки** (DOCX/PDF/«Собрать том») считается в Python по той же
разметке Word и тоже учитывает несохранённые правки: `_paginate_docx` принимает
`overrides` с текстом абзацев, поэтому дописанный текст добавляет листы и в
собранном томе.


### Редактирование пояснительной записки из окна программы

> **Статус: реализовано.** Текст исходного DOCX пояснительной записки можно править
> **не выходя из программы** и **по листам** — так, как они попадут в том.

**Открытие редактора — из свойств документа:**

- кнопка **«Редактировать ПЗ…»** в свойствах документа (панель справа) — только для DOCX
  (для PDF кнопка заблокирована с подсказкой, т.к. PDF не редактируется). Пункта меню
  «Редактировать пояснительную записку…» нет.

**Окно редактора (`app/ui/pz_editor.py`, `PzEditorDialog`):**

| Элемент | Назначение |
|---------|------------|
| Список листов (слева) | **Все листы** записки («Лист 1 — N абз.»). Разбивка выполняется той же пагинацией, что и предпросмотр/сборка (`preview_html._paginate_docx`), поэтому число и состав листов совпадают |
| Область текста (справа) | Текст абзацев выбранного листа — редактируется как обычный текст |
| «← Предыдущий лист» / «Следующий лист →» | Переход между листами; правки сохраняются в буфере при переключении |
| «Сохранить в файл» | Записывает правки в исходный DOCX (при первом сохранении рядом создаётся `*.docx.bak`) |
| «Отмена» | Закрывает окно **без** изменений файла |

**Что сохраняется, а что нет:**

- меняется **текст абзацев** DOCX; форматирование абзаца сохраняется (правка идёт в первый `run`);
- **таблицы, изображения, колонтитулы и разметка страниц не удаляются** и остаются на месте;
- абзацы внутри таблиц не редактируются (в списке листов показываются только абзацы тела документа);
- пустые абзацы в редакторе не показываются — они сохраняются без изменений.

**Связь с моделью:** после сохранения число листов документа пересчитывается
(`normalize_file`) и обновляются предпросмотр и дерево тома, поэтому новые листы сразу
видны в предпросмотре ПЗ и учитываются в содержании и нумерации.

### Предпросмотр пояснительной записки во встроенном Word

> **Статус: реализовано.** Листы пояснительной записки показываются **настоящим
> Word**, а не HTML-вёрсткой: в области предпросмотра открывается документ,
> который уже собран с автоматическим оглавлением и номерами листов. Текст
> правится привычными средствами Word (лента, курсор, проверка орфографии).

**Зачем.** HTML-предпросмотр повторяет лист ГОСТ, но не является Word: разбивка
на листы, положение таблиц и вид оглавления в нём — модель, а не оригинал.
Для записки показывается оригинал, поэтому «как в Word» совпадает с тем, что
попадёт в том по определению.

**Как это сделано** (`app/core/word_preview.py`, `app/ui/word_host.py`):

- документ собирается **штатным кодом раздела** (`docx_exporter.build_section_docx`)
  во временный файл — со оглавлением, закладками `MIMO_H`, номерами листов и
  основными надписями;
- Chromium не умеет держать нативное окно, поэтому окно Word переносится внутрь
  виджета (`SetParent`, стиль `WS_CHILD`). OLE-контейнер
  `QAxWidget("Word.Document.8")` для этой задачи не годится: файл в него
  загрузить не удалось — Word создаёт пустой документ «Без имени»;
- встраивание **самовосстанавливающееся**: Word — отдельный процесс и может
  пересоздать окно (смена вида, диалог), тогда `WordHost._check_state` раз в
  такт возвращает окно на место;
- рабочая копия лежит в **системном временном каталоге**
  (`%TEMP%\tom_builder_preview`), а не в каталоге проекта: проект находится в
  синхронизируемой папке (YandexDisk), и её клиент мешал Word открывать файл —
  вызов `Documents.Open` зависал. Во временном каталоге файл открывается за
  полсекунды и не попадает в git;
- собранный файл переводится в **режим совместимости Word 2013+**
  (`w:compatibilityMode` 14 → 15, удаляется `w:useFELayout`). Шаблон python-docx
  объявляет Word 2010, и Word 2016/2019 открывает такой файл в «режиме
  ограниченной функциональности», где **правка запрещена**;
- если файл всё же занят другим экземпляром Word, он открывается из копии во
  временном каталоге — вместо диалога «Файл уже используется».

**Правки и пересборка.**

- правки остаются в **рабочей копии**; исходный DOCX записки не меняется;
- при изменении реквизитов, шрифтов или структуры тома копия помечается
  **устаревшей** (кнопка «Пересобрать листы» подсвечивается), но сама **не
  пересобирается** — иначе несохранённые правки в Word пропали бы молча;
- кнопка «Пересобрать листы» сохраняет правки в копию и собирает документ
  заново по текущим настройкам;
- при закрытии окна программы Word закрывается (правки сохраняются), временные
  файлы удаляются, если в HTML-предпросмотре не осталось несохранённых правок.

**Когда Word недоступен** (не установлен, сбой COM): предпросмотр откатывается
на прежнюю HTML-вёрстку, причина выводится на панели. Для остальных листов тома
(обложка, титул, содержание, состав, изменения, графическая часть, приложения)
HTML-предпросмотр остаётся основным.

| Файл | Роль |
|------|------|
| `app/core/word_preview.py` | рабочая копия: сборка, кэш по состоянию источников, режим совместимости, свободные имена |
| `app/ui/word_host.py` | окно Word внутри виджета: открытие, встраивание, сохранение, закрытие |
| `app/ui/preview_widget.py` | выбор режима: ПЗ → Word, остальные листы → HTML |

### Правка текста и таблиц ПЗ прямо в предпросмотре (без отдельного окна)

> **Статус: реализовано.** Абзацы и **ячейки таблиц** пояснительной записки редактируются
> **inline в самом предпросмотре страниц** — отдельное окно открывать не нужно.

> **Для пояснительной записки это резервный путь.** Основной показ листов ПЗ —
> встроенный Word (см. раздел выше): в нём правка идёт средствами Word, а
> HTML-вёрстка остаётся для остальных листов тома и на случай, когда Word
> недоступен.

**Как это работает:**

- когда в дереве выбран **документ ПЗ (DOCX)**, либо **раздел «Пояснительная записка»**,
  абзацы в предпросмотре становятся редактируемыми (`<p class="pz-para" contenteditable>`);
- абзац адресуется парой **`data-para-file` (путь DOCX) + `data-para-index` (индекс абзаца
  в `document.paragraphs`)** — тот же порядок, что использует пагинация предпросмотра;
- при вводе JS-мост вызывает `bridge.onParagraphChanged(index, file, text)`;
- правка **накапливается в памяти** и применяется к уже отрисованным листам (overrides),
  поэтому она **не пропадает** при перерисовке листа и при переходах по дереву;
- **файл при этом не изменяется** — запись выполняется только по нажатию кнопки.

**Таблицы ПЗ.** Таблицы в предпросмотре рисуются CSS-grid с фактическими ширинами колонок
из `w:tblGrid` исходного DOCX, поэтому предпросмотр совпадает с исходным документом.
Каждая ячейка редактируется (`<div class="dt-cell pz-cell" contenteditable>`):

- адрес ячейки — **`data-table` / `data-row` / `data-cell`** (индексы в `document.tables`),
  тот же путь, по которому выполняется запись в файл;
- при вводе JS-мост вызывает `bridge.onTableCellChanged(table, row, cell, file, text)`;
- правка **накапливается в памяти** (отдельно от правок абзацев) и применяется к уже
  отрисованным листам, поэтому не пропадает при перерисовке и переходах по дереву;
- **объединённые ячейки** (`w:gridSpan` / `w:hMerge` / `w:vMerge`) не дублируют текст:
  начало **горизонтального** объединения растягивается на свой `col_span`, поглощённые
  ячейки не рисуются вовсе (иначе они наложились бы на объединение и строка «поехала»);
  ячейки-продолжения **вертикального** объединения рисуются пустыми, но **с рамкой** и на
  своём `col_span` — иначе в строке остаётся «дыра» и таблица выглядит разорванной.
  Поэтому текст показан один раз — в начале объединения.
  Вертикальное объединение намеренно не выводится как `grid-row:span`: при переносе таблицы
  на следующий лист начало объединения остаётся на предыдущем листе, и продолжение оказалось
  бы без текста. Правки всегда записываются в ячейку-начало (`document.tables[t].rows[r]
  .cells[c]` разрешает адрес внутри объединения, Word перенаправляет запись в начало);
- **сетка строк выравнивается по колонкам `w:tblGrid`**, а не по числу физических `w:tc`
  (`docx_reader.table_grid_cells`). Word описывает объединения двумя способами
  (`w:gridSpan` и legacy `w:hMerge`), причём в одном файле они встречаются вместе; подсчёт
  `w:tc` давал лишние колонки — правые ячейки уезжали за границу таблицы и вставали со
  сдвигом по вертикали (так «разваливалась» колонка «Пол» в штатном расписании).
  `python-docx` сам разрешает объединения по сетке: `row.cells` даёт по одной ячейке на
  колонку, повторяя объединённую, поэтому совпадение элемента `w:tc` и есть признак
  объединения. В каждой строке ровно столько ячеек, сколько колонок в таблице;
- **высота строки при пагинации** (`_estimate_table_row_h`) считается по ширине,
  **просуммированной по занятым колонкам** (`col_span`), плюс отступы и рамка ячейки
  (`_TABLE_CELL_PAD_MM`, `_TABLE_CELL_BORDER_MM`). Оценка по одной узкой колонке завышала
  строку в разы (таблица рвалась по строке на каждый лист), а без отступов — занижала
  (таблица уезжала за нижнюю границу листа и обрезалась);
- многострочный текст ячейки (переносы строки) раскладывается по абзацам ячейки;
- при переносе таблицы на следующий лист первая строка повторяется как шапка и над ней
  выводится строка **«Продолжение таблицы»**.

**Автосохранение в связанный DOCX.** Правки абзацев и ячеек таблиц записываются в
исходный файл **сами**, без нажатия кнопки:

| Когда | Что происходит |
|-------|----------------|
| Остановка ввода | Через `AUTOSAVE_DELAY_MS` = 1000 мс (`preview_widget`) правки уходят в DOCX одним сохранением файла |
| Переключение листа / документа | `flush_autosave()` дописывает накопленное **до** перерисовки — правки не теряются при переходах по дереву |
| Сборка, экспорт, закрытие, смена проекта | `flush_autosave()` в `_confirm_pending_pz_edits` — сначала запись, и только если что-то всё же не записалось, задаётся вопрос «Сохранить / Отменить / Не сохранять» |
| Ошибка записи | Причина пишется в `tmp/build.log`, пользователю показывается сообщение (молча правки не теряются) |

Запись идёт **в тот же файл**, к которому привязан лист (`data-para-file` листа =
путь DOCX проекта). При первом сохранении рядом создаётся резервная копия
`*.docx.bak`. Предпросмотр при автосохранении **не перерисовывается** — иначе
сбросился бы курсор посреди ввода; лист уже показывает введённый текст.

**Отложенный пересчёт листов.** Пагинация документа занимает около секунды, поэтому
после автосохранения число листов пересчитывается не сразу: путь попадает в
`_pages_dirty`, а `_refresh_dirty_pages()` вызывается, когда число действительно
нужно — при перерисовке листа, переключении по дереву и перед сборкой.

**Кнопка «Сохранить правки ПЗ (N)»** остаётся в панели предпросмотра как индикатор:
появляется с числом несохранённых правок (обычно на секунду, пока идёт пауза
автосохранения) и позволяет записать их немедленно. Запись выполняется тем же
путём — `app/core/docx_edit.py::apply_docx_edits`, за одно открытие/сохранение файла.

**Защита от потери правок.** Перед закрытием программы, сборкой тома/раздела,
экспортом, созданием и открытием проекта сначала вызывается автосохранение
(`flush_autosave`); если после него несохранённые правки всё ещё есть (например,
запись не удалась), программа спрашивает **Сохранить / Отменить / Не сохранять**
(`_confirm_pending_pz_edits`). При «Отменить» действие не выполняется.

**Общий модуль записи.** Все пути правки используют один модуль `app.core.docx_edit`:

- `apply_docx_edits(path, {абзац: текст}, {"т:с:я": текст})` — абзацы и ячейки таблиц
  за одно сохранение файла (этим путём идёт inline-правка в предпросмотре);
- `apply_paragraph_edits(path, {индекс: текст})` — только абзацы (окно редактора ПЗ);
- `apply_table_cell_edits(path, {"т:с:я": текст})` — только ячейки таблиц.

Сохраняются таблицы, изображения, колонтитулы и разметка страниц; изменяется только текст
указанных абзацев/ячеек; создаётся резервная копия `*.docx.bak`.

**Когда правка недоступна:**

- для **PDF**-записки (PDF не редактируется) — абзацы и таблицы не становятся редактируемыми;
- для графической части, приложений, обложки, титула, содержания и листа изменений —
  это не текст ПЗ, поэтому разметка правки не создаётся;
- в **собранных** HTML/PDF-файлах редактируемая разметка не выводится — итоговый документ чистый.
### Дерево «Листы тома» — управление структурой

> **В дереве только разделы тома.** Документы и приложения в дерево не
> выводятся: список отражает состав тома, а не файлы. Управление документами
> раздела (добавление, флажок «В сборку», удаление) — в контекстной панели
> справа, блок «Документы раздела». Вторая колонка «Листы» показывает число
> листов раздела по единому источнику нумерации (`toc.build_layout`).

- **Перестановка местами** — кнопки «Вверх»/«Вниз»: меняют порядок **разделов** тома. Порядок блоков сохраняется в модели (`structure`) и используется при сборке (содержание, PDF, DOCX).
- **Отметка «необходимость»** — чекбокс у раздела. Снятая отметка **исключает раздел из сборки**: он не попадает в DOCX/PDF, не считается в «Листов M», не отображается в содержании.
- **Удалить** — недоступно: разделы не удаляются (структура задаётся порядком). Документы и приложения удаляются в контекстной панели.
- **Добавление документов/приложений** — вынесено в **свойства** (панель справа): в свойствах раздела «Пояснительная записка»/«Графическая часть» есть кнопка «Добавить документ…»; приложения добавляются в форме «Приложения».

### Содержание — только разделы тома

`toc.content_rows` группирует позиции карты листов **по разделам**: документы
внутри раздела объединяются в одну строку. Поэтому в содержании нет имён файлов,
и число строк равно числу разделов. Карта листов (`toc.build_layout`) при этом
по-прежнему хранит позиции по документам — она нужна для сквозной нумерации и
закладок PDF.

**Приложения — каждое отдельной строкой.** Приложения не склеиваются с разделом:
у каждого своя строка, своё обозначение и своё название. Наименование — название
приложения (`Appendix.name`), обозначение — «Приложение N»
(`toc.appendix_designation`: «Приложение 1», «Приложение А»; без номера —
«Приложение»), в графе «Листы» — номер первого листа приложения. Раньше все
приложения сводились в одну строку «Приложения» с номером первого в обозначении.

**Графа «Листы» — только номер первого листа раздела.** В строке стоит число,
с которого начинается раздел: `3`, а не «Листы 3 — 10» и не «Лист 3». Слова
«Лист»/«Листы» и диапазон в графу не выводятся (`toc._row_sheets`). Позиции,
не занимающие лист (обложка, титул, ручные строки без нумерации), дают «—».

Пустые разделы (нет включённых документов) строк в содержании не дают.

**Число листов раздела ПЗ — по собранному разделу, а не по исходной записке.**
Собранный раздел занимает больше листов, чем исходный DOCX: рамки, штампы,
оглавление и оформленные таблицы съедают место. Поэтому `toc.build_layout`
принимает `pz_pages` — фактическое число листов раздела, а `build_layout`/
`content_rows` без него берут значение из рабочей копии предпросмотра
(`word_preview.preview_page_count`, измерено Word).

**Двухпроходная сборка тома** (`docx_exporter.build_text_docx_with_content`).
Содержание строится раньше раздела ПЗ, поэтому число его листов известно только
приблизительно. После первой сборки том измеряется по закладке `MIMO_PZSTART`
(`measure_pz_sheets`), и если содержание разошлось с фактом, том пересобирается
с уточнённым значением — максимум два прохода. Приложение сборки
(`app.ui.build_worker`) вызывает именно эту обёртку.

**Измерение готового тома — через копию во временном каталоге.** Word зависает
на файлах внутри синхронизируемой папки (Яндекс.Диск): `Documents.Open` не
возвращается. Поэтому `measure_pz_sheets` копирует файл в `%TEMP%` и открывает
копию. Границы раздела читаются по `Information(3)` — физический номер страницы;
`Information(1)` даёт номер с перезапуском внутри раздела и для счёта листов
тома не подходит.

**Геометрия таблицы содержания.** Три колонки фиксированной ширины в мм —
Наименование 95 | Обозначение 50 | Листы 40 (`models.TOC_WIDTHS`, сумма 185 мм =
вся ширина между линиями рамки). Разметка — настоящая `<table>` с `<colgroup>`,
`table-layout: fixed` и **полной сеткой границ**: у каждой ячейки рамка 0.25 мм со
всех сторон плюс внешний контур (раньше строки были flex-строками с ширинами
34/18 мм и только подчёркиванием, и таблица не доходила до рамки). В HTML ширины
переводятся в проценты от суммы (`preview_html._cols_html`): 185 мм не делятся на
целое число пикселей, и браузер округлял ширину вверх на 1 px — правая линия
таблицы выходила за линию рамки. В Word те же ширины задаются сеткой таблицы
(`docx_exporter._add_content`), поэтому предпросмотр, HTML-том, PDF и Word
совпадают. Замер в QtWebEngine: ширина таблицы 185.0 мм, смещение от левой и
правой линии рамки — 0.002 мм.

### Поля и их редактирование

- Каждое поле — `span[contenteditable]` с `data-key` (организация, шифр, объект, наименование тома, стадия, город, год).
- Клик по полю → inline-редактирование прямо в HTML.
- При вводе JS-мост вызывает `bridge.onFieldChanged(key, value)` → Python обновляет **модель** (единый источник).
- Правка значения обновляет его **везде**: т.к. лист перерисовывается из свежего «снимка» данных при выборе.

### Подписи

- Поле подписи (`data-kind="signature"`) отображает **изображение подписи** (или плейсхолдер) + Фамилию.
- Клик по полю подписи → `bridge.onSignatureClicked(key)` → Python открывает диалог выбора подписанта из реестра.
- Назначенная роль (`develop`/`check`/`norm`/`approve`) хранится в `signature_assignments` и применяется на **всех** листах.
- Строки подписей штампа (форма 5 — пять строк, форма 3 — шесть) заполняются прямо в
  предпросмотре; подпись в графе «Подп.» подбирается по фамилии строки (см. ниже).
- **Подсказка «(подпись)» — только в предпросмотре.** Если подпись не выбрана, в
  интерактивном предпросмотре графа показывает серый плейсхолдер, а в собранном томе
  (HTML, PDF, DOCX) она остаётся **пустой**: сборка ставит в снимок
  `hide_signature_hint = True`, и `_sig_field` / `_cell_sig_image` не выводят текст
  (дополнительно `.sig-placeholder` скрыт в `_html_document`). Иначе в готовом
  документе печатался служебный текст. Изображение реальной подписи выводится как есть.
- **Изображения встраиваются как `data:`-URI** (`preview_html.signature_src`): подписи и
  логотип графы 9 читаются с диска и попадают в разметку в base64. Ссылку `file:///…`
  страница предпросмотра и панели штампа открыть не может — они грузятся через
  `setHtml(…, about:blank)`, и QtWebEngine блокирует доступ к локальным файлам, поэтому
  картинка молча не отображалась (в графе оставалась пустая рамка). Дополнительно у
  обоих `QWebEngineView` включён `LocalContentCanAccessFileUrls`. Прочитанные файлы
  кэшируются в `_SIG_IMG_CACHE` (подписи повторяются на всех листах со штампом).
- **Белые поля подписи обрезаются** (`_signature_pixmap`): скан росчерка почти всегда
  снят вместе с полями, и при вписывании картинки целиком в графу 15 × 5 мм сам росчерк
  получался в несколько миллиметров. Границы «чернил» ищутся по порогу
  `_SIG_WHITE_LEVEL` с запасом `_SIG_PAD_RATIO`, поэтому в ячейку вписывается росчерк.
- **Подпись может выходить за ячейку до 1.5×** (`SIGNATURE_OVERFLOW`): живой росчерк в
  графу 15 × 5 мм не помещается, поэтому он центрируется по ячейке и перекрывает её
  линии, как при подписывании от руки. В HTML — `width/height:150%; object-fit:contain`
  при `overflow:visible` (контейнер ячейки больше не клипует); в Word и PDF тот же
  коэффициент применяет `signature_fit_mm(…, overflow=1.5)`, так что предпросмотр, DOCX
  и PDF дают одинаковый размер подписи.

### Заполнение штампа прямо в предпросмотре

> **Статус: реализовано.** Все ячейки левого блока основной надписи правятся inline
> (должность, фамилия, подпись, дата); правка уходит в модель и попадает в Word и PDF.

| Что правится | Ключ поля | Куда пишется |
|--------------|-----------|--------------|
| Должность строки подписи | `sp\|<раздел>\|<строка>\|post` | `stamp_signatures["*"][<строка>].post` |
| Фамилия строки подписи | `ss\|<раздел>\|<строка>\|surname` | `stamp_signatures["*"][<строка>].surname` |
| Дата строки подписи | `sp\|<раздел>\|<строка>\|date` | `stamp_signatures["*"][<строка>].date` |
| Графа «Подп.» (выбор подписанта) | `ss\|<раздел>\|<строка>\|signature` | `stamp_signatures["*"][<строка>].surname` |
| Старый ключ даты (совместимость) | `sd\|<раздел>\|<роль>` | `stamp_changes[<раздел>].sign_dates` |
| Ячейка таблицы изменений | `ch\|<раздел>\|<строка>\|<колонка>` | `stamp_changes[<раздел>].rows` |
| Обозначение, объект, стадия, графа 9 | `volume_id`, `object_name`, `stage`, `organization` | `Requisites` |

**Подписи ОБЩИЕ для всех штампов.** Должности, фамилии, подписи и даты в штампах
содержания, пояснительной записки и графической части заполняются одинаково:
правка в любом штампе сразу применяется во всех остальных. Правки хранятся под
одним ключом `stamp_signatures["*"]` (`models.STAMP_SIG_SHARED`), а не по
разделам. `<раздел>` в ключе поля остаётся (по нему адресуется лист), но на
хранение значения не влияет.

**Связь строк формы 5 и формы 3 — по «слотам» (`models.STAMP_SIG_SLOTS`).**
У записки (форма 5) и графической части (форма 3) разное число строк, поэтому
данные переносятся не по номеру строки, а по схеме:

| Строка ПЗ / содержания | Строка ГЧ | Что это |
|------------------------|-----------|---------|
| 1 | 1 | Разраб. |
| 2 | 2 | свободная |
| 3 | 3 | свободная / Пров. |
| 4 | **5** | Н.контр. |
| 5 | **6** | ГИП |

Строка **4 формы 3 остаётся свободной** — ей не соответствует ни одна строка
записки, поэтому правка в ней не сохраняется. Без этой карты данные
переносились бы по номеру строки, и «Н.контр.» с «ГИП» из записки попадали бы
в графику не на свои места.

Хранение правок идёт по слоту (`1..5`), поэтому одна правка действует и в
форме 5, и в форме 3. `models.set_stamp_signature(..., form=5|3)` переводит
номер строки в слот; форма определяется по разделу
(`main_window._stamp_row_form`: графика → 3, остальные → 5).

Старые проекты, где правки лежали по разделам, подхватываются: при чтении
берётся первый непустой набор (приоритет у текущего раздела), а первая же
правка переносит его в общий ключ.

**Строки подписей — единый источник `models.stamp_signature_rows(project, kind, form)`.**
Формы 5 и 3 имеют разное число строк (`models.STAMP_SIG_ROWS`): у формы 5 пять строк
(15/20/25/30/35 мм от верха штампа), у формы 3 шесть (25/30/35/40/45/50 мм). Каждая строка
несёт роль (`develop`/`check`/`norm`/`approve` или пустую — свободная строка), должность по
умолчанию, фамилию из реестра подписантов и изображение подписи, **подобранное по фамилии**
(`signer_signature_image`).

- **Хранятся только правки.** `project.stamp_signatures["*"]` содержит изменённые поля,
  значения по умолчанию берутся из формы и реестра — поэтому смена подписанта в реестре
  продолжает обновлять незатронутые строки. Запись — `models.set_stamp_signature`
  (`main_window._apply_stamp_edit`).
- **Подпись подбирается по фамилии, а не по роли**: правка фамилии в графе сразу меняет
  изображение подписи (в предпросмотре — скриптом `syncSigPreview`, в Word/PDF — при сборке).
- **Клик по графе «Подп.»** открывает выбор подписанта для строки
  (`main_window._stamp_row_ref`); выбранная фамилия пишется в ту же строку.
- Должности по умолчанию («Разраб.», «Н.контр.», «ГИП.») — редактируемые значения, а не
  статичные надписи: строку можно переименовать или оставить пустой и заполнить вручную.
- `<раздел>` — ключ раздела листа (`content`, `Пояснительная записка`, …). `MainWindow`
  проставляет `snapshot["section"]` **всем** листам: иначе ключ правки получал пустой раздел
  и значение не попадало в проект.
- Значения хранятся **по разделам**: у каждого раздела свои строки подписей и своя таблица
  изменений, как и в самой основной надписи.
- **Те же значения выводятся в Word и PDF**: `docx_exporter._add_stamp_table` получает
  `signature_rows` и заполняет должность/фамилию/дату, а в графу «Подп.» вставляет
  изображение (`_insert_signature_image`); `renderer._layout` строит те же ячейки
  (`sig_post`/`sig_name`/`sig_sign`/`sig_date`) и рисует подпись `_draw_signature_image`.
  Раскладка строк в Word/PDF — `geometry.stamp_signature_rows(form)`, поэтому строки
  совпадают с предпросмотром.
- **Ограничение:** колонки граф 14–19 (таблица изменений) размечены в сетке форм 5/3 только
  в строке заголовка — свободных рядов под значения геометрия ГОСТ не предусматривает.
  Поэтому ячейки `ch|` в HTML пока не выводятся (модель и запись правок готовы); появятся
  вместе с пересмотром сетки. Строка значений первой строки подписей («Разраб.»)
  одновременно служит строкой значений таблицы изменений — как на образце формы.

### Единый источник данных

`app/core/preview_model.py::build_preview_snapshot(project)` собирает из проекта один снимок (реквизиты + роли подписей + изменения + разделы). Все листы HTML-предпросмотра рендерятся из этого снимка. Поэтому правка одного значения распространяется на все листы.

### Графа 9 — организация: текст или логотип

> **Статус: реализовано.** Графа 9 по ГОСТ Р 21.101-2020 (приложение Ж) — «наименование
> или различительный индекс организации, разработавшей документ». Заполняется **двумя
> способами на выбор** (панель справа, форма реквизитов, группа «Графа 9 основной надписи»):

| Режим | Что выводится |
|-------|---------------|
| **Текст** | Наименование организации («Организация» в реквизитах) **по центру** ячейки |
| **Логотип** | Изображение из **PDF-файла**, автоматически масштабируется под ячейку |

**Где находится ячейка:**

| Форма | Ячейка графы 9 (от левого-верхнего угла штампа) | Размер |
|-------|------------------------------------------------|--------|
| **5** (первый лист текста) | x 135…185, y 25…40 мм | 50 × 15 мм |
| **3** (графический лист) | x 135…185, y 40…55 мм | 50 × 15 мм |
| **6** (последующие листы) | **графы 9 нет** (по ГОСТ) | — |

Границы блока проверены по эталонам («Форма 3.pdf» = форма 5, «Форма 5.pdf» = форма 3):
вертикали x 150 и 165 обрываются на y 25, поэтому ниже строки «Стадия | Лист | Листов»
(135…185, y 15…25) правый блок — это одна ячейка графы 9. **Содержимое графы 9
центрируется по горизонтали И по вертикали**; длинное наименование переносится на
строки, и блок текста остаётся по центру ячейки.

**Логотип (PDF → PNG).** Word не умеет вставлять PDF как картинку, поэтому PDF
растеризуется один раз в PNG (модуль «app/core/logo.py»):

1. пробный рендер при 150 dpi — определяются границы «непустой» области;
2. рендер **только этой области** с зумом до ~1400 px по большей стороне
   (ограничение 4 млн пикселей) — логотип получает полиграфическое разрешение,
   но каталог «tmp/logo_cache» не заполняется «мегабитмапами».

Результат кэшируется (ключ — путь + mtime + параметры) и пересобирается только при
изменении файла. В каждом выводе логотип **вписывается в ячейку с сохранением
пропорций**: в HTML — «object-fit:contain», в Word — расчёт размера в мм, в PDF —
«insert_image» в рассчитанный прямоугольник. Логотип не искажается и не выходит за
рамку ни при какой пропорции исходного PDF.

**Центрирование.** Текст графы 9 центрируется по обеим осям:

- HTML — контейнер «display:flex; align-items:center» (вертикаль) + поле
  «display:block; width:100%; text-align:center» (горизонталь);
- PDF — «_vcenter_rect» (сдвиг блока текста к центру ячейки) + «TEXT_ALIGN_CENTER»;
- Word — «WD_ALIGN_PARAGRAPH.CENTER» + вертикальное выравнивание ячейки «center».

**Переполнение текстом.** Длинное наименование организации не вылезает за рамку графы:
в HTML кегль уменьшает JS-автоподгонка (класс «fit-lbl» — и в предпросмотре, и в
собранном HTML; проверяются и ширина, и высота), в PDF — подбор кегля (минимум 5 pt).

**Единый источник значения (текстовый режим).** Текст графы 9 — это реквизит
**«Организация»**: правка поля прямо в графе 9 меняет наименование на обложке,
титульном листе и во всех основных надписях. Режим («текст / логотип») и файл
логотипа хранятся отдельно в «project.stamp_cell9» и сохраняются в JSON проекта.

### Запуск WebEngine

В `main.py::setup_webengine_env()` задаются флаги (`--no-sandbox --disable-gpu
--disable-software-rasterizer --disable-dev-shm-usage`), каталог данных WebEngine
(в `tmp/qt_webdata`), чтобы QtWebEngine корректно запускался в локальных средах.
На машине пользователя GPU доступен — эти флаги не мешают.

**`--single-process` намеренно НЕ используется.** В нём Chromium держит сетевой
поток и очередь ввода в одном процессе с GUI; после переключения в другую
программу и возврата в окно очередь ввода перестаёт обрабатываться — кнопки в
окне не нажимаются до перезапуска. Без этого флага QtWebEngine запускает
вспомогательные процессы штатно.

**Возврат фокуса в окно.** `MainWindow.changeEvent` ловит `ActivationChange` и при
активации окна вызывает `_restore_input_focus()`: он заново ставит фокус на
активный виджет (или на предпросмотр, если прежний стал скрыт/недоступен) и
отправляет странице WebEngine `window.focus()` + событие `focus` на `body`.
Без этого активным оставалось поле внутри `QWebEngineView`, потерявшее фокус на
уровне Windows, и ввод «залипал». Действие повторяется дважды (60 и 220 мс):
Windows отдаёт фокус окну уже после прихода события.

## 7. Стек и библиотеки

**Версия Python: 3.12 (64-бит) — обязательна.** Зависимости поставляются готовыми в
`vendor/` и содержат бинарные модули, собранные под CPython 3.12
(`lxml/etree.cp312-win_amd64.pyd`, `pywin32` cp312). На другой версии Python импорт
`lxml` падает, из-за чего не загружается `python-docx` и **DOCX не отображается в
предпросмотре**. Установка, причины и признак неверной версии — **PYTHON.md**;
проверка — `py -3.12 -c "import docx, pymupdf, PySide6; print('OK')"`.

| Назначение | Библиотека | Почему |
|-----------|-----------|--------|
| GUI | **PySide6 (Qt)** | Нативный десктоп, деревья/таблицы, предпросмотр |
| DOCX | **python-docx** | Чтение/создание .docx, таблицы для осн. надписи |
| DOC→PDF | **pywin32 (Word COM)** | Родной Word = точное соответствие; Word установлен |
| PDF чтение/сборка | **PyMuPDF (fitz)** | Геометрия страниц, вставка листов в родных размерах, векторная отрисовка |
| PDF векторные надписи | **reportlab** (или PyMuPDF-рисование) | Графы осн. надписи как вектор, без растеризации |
| Упаковка в exe | **PyInstaller** | Один файл/папка для пользователя |

## 8. Конвейер сборки и экспорта

**DOC (текстовый):**
1. Собрать титул + содержание + ПЗ + **лист регистрации изменений** в python-docx.
2. Страница А4, поля по ГОСТ, осн. надпись форма 2 (1-й лист) / 2а (последующие) — таблицами внизу листа + колонтитулы.
3. Содержимое ПЗ импортируется из DOCX-исходников с **переоформлением** под ГОСТ (шрифт ISOCPEUR, поля, формат листа); таблицы и рисунки внутри ПЗ сохраняются смыслово.
4. Экспорт в DOCX (текст) — **без графики и без приложений**.

**PDF (полный том):**
1. Собрать DOCX → конвертировать в PDF через **Word COM** → PDF-текст (титул + содержание + ПЗ + лист изменений).
2. Взять графические листы из входных PDF: каждый лист **в родном размере**, наложить векторную рамку + осн. надпись форма 1 (PyMuPDF/reportlab).
3. Вставить **приложения PDF**: с заголовком «Приложение …», листы на родных размерах (или на А4 — по конфигурации), пересчёт листов.
4. **Слить** PDF-текст + графику + приложения в единый PDF в правильном порядке.
5. Проставить сквозную нумерацию «Лист N / Листов M».
6. Автосоздать закладки/оглавление в PDF (наработка из «АвтоЗакладкиПДФ»).

> Итог: текст отрисован самим Word (гарантированно как в исходнике), графика/приложения — на своих размерах. Без потери качества/масштабирования.

- фоновая обработка/прогресс при длительных операциях (Word COM, вставка крупных PDF);
- повторяемость: сохранение сборочного задания (включая журнал изменений и список приложений) для пересборки тома.

## 11. Этапы разработки

1. **Скелет UI + форма реквизитов + модель тома** — согласование полей на реальном примере.
2. **Нормализация входа**: DOCX→текст, PDF→страницы+геометрия.
3. **Оформляющий слой ГОСТ**: титул, содержание, осн. надписи ф.3/5/6, рамка, ISOCPEUR.
4. **Рендер PDF-текста** через Word COM (проверка точности).
5. **Рендер графических листов** + слияние в полный PDF (+ закладки).
6. **Подписи**: реестр, импорт изображений, раскладка по Фамилии.
7. **Журнал изменений**: форма, ведение, автогенерация листа регистрации изменений, пересчёт нумерации.
8. **Приложения**: добавление PDF, нумерация, вставка, внесение в содержание.
9. **Предпросмотр + отчёты о сборке**.
10. **Упаковка (PyInstaller) и тест на реальных томах**.

## 12. Риски и открытые вопросы

- **Точная отрисовка основной надписи** — самая трудоёмкая часть; зависит от PyMuPDF/reportlab.
- **DOC→PDF** через Word COM требует установленного Word (подтверждено — есть). Фоновая обработка COM обязательна.
- **Произвольные размеры листов** в графике — политика (оставляем родной размер; поворот/масштаб — на конфигурацию).
- **ISOCPEUR в Word** — корректно только при наличии шрифта в системе; нужен fallback/встраивание.
- **Разбор DOCX с чужой вёрсткой** — риск потери элементов при переоформлении; тестировать на реальных файлах.

## 13. Анализ аналогов (по результатам интернет-поиска)

> Поиск проведён через внешний поисковый движок (встроенный веб-поиск DeepSeek был недоступен из-за ошибки авторизации). Ниже — классификация рынка.

### Категория 1. CAD/СПДС-надстройки (сильнейший сегмент)
- **СПДС GraphiCS** — оформление ПТД по ГОСТ внутри AutoCAD/nanoCAD: рамки, осн. надписи, размеры, шрифт ISOCPEUR. → инструмент **создания** чертежа.

### Категория 2. Формирование тома внутри отраслевой CAD
- **IndorTrafficPlan** — формирование ПД в виде единого тома; настраиваемый шаблон.
- **sodislab.com** — автовставка «состава проектной документации» с рамками.

### Категория 3. Утилиты слияния PDF (без ГОСТ)
- **АвтоЗакладкиПДФ (KDMsoft)** — объединение PDF + автозакладки.
- **Adobe Acrobat / iLovePDF / Smallpdf / PDF2Go** — «тупой» конкатенатор (по сути способ вставки приложений, но без ГОСТ).

### Категория 4. Платформы автоматизации ПД (SaaS/BIM/ПТО)
- **KPD Проект** — цифровизация ПД, статусы/изменения.
- **24ПТО, проПТО** — исполнительная документация, журналы/реестры, OCR.
- **Vitro-CAD** — BIM-платформа совместной работы.

### Категория 5. Шаблоны/бланки ГОСТ (не программы)
- Рамки А4 со штампом (buildingclub, logoslab, isopromat), трафареты Visio (**td-visio**).

### Вывод
**Прямых аналогов нет.** Ниша свободна для программы, которая:
> принимает **произвольные файлы заказчика** (Word + PDF, любые размеры листов) и собирает **готовый том полностью по ГОСТ** (титул, содержание, рамки, осн. надписи, сквозная нумерация, подписи по ФИО, **журнал изменений**, **приложения**) с двойным выводом **DOC + PDF**.

Рынок делится на два полюса:
1. **Инструменты проектировщика** (CAD/СПДС) — создают документацию изнутри, но не собирают чужие файлы в готовый том.
2. **Конкатенаторы PDF** — собирают что угодно, но без ГОСТ-оформления.

Наша программа — недостающее звено между ними, с бонусом: полная десктопная автономность, приём произвольных форматов, двойной вывод DOC+PDF, журнал изменений и приложения по ГОСТ.
